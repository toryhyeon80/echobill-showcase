## 1. Critical — 서로 다른 기준 (기획서에 맞춤)

### 1.1 초기 AI 모델 / 하이브리드

| 문서 | 지시 |
|---|---|
| 기획서 · 모델 가이드 | 클라우드 STT + 클라우드 LLM. 초기 Baseline **GPT-4o-mini** (근거: 모델 가이드 PM 확정 사항 — 기획서 §6.1은 예시로만 언급, [DL-11](#dl-11-초기-llm모델-비교-확정)). 정확한 제품·버전은 **D01**. 로컬 SLM·하이브리드 라우팅은 **핵심 QA 후 선택** |
| WBS · 레퍼런스 · 디자인 | Gemma 로컬 → Claude 체이닝이 본선처럼 기술 |

**확정 (기획서):**
- MVP 기본 경로: **클라우드 LLM (초기 GPT-4o-mini)** + **Rule 폴백**
- Gemma / Claude / Ollama 체이닝: **선택 실험** (E2E·QA 완료 후, 시간 남을 때만)
- WBS 1~2단계 문구는 「클라우드 LLM 연동 + Rule」로 해석·수정

---

### 1.2 정확도 95%

| 문서 | 지시 |
|---|---|
| 기획서 · 모델 가이드 | 95% = **연구 목표(Stretch)**. 미달만으로 배포 중단 **아님**. 운영 전환 선은 **80%** (개선 비교용 Golden) |
| WBS 3단계 | Golden 기준 **95% 도달**이 목표처럼 기술 |

**확정 (기획서):**
- 배포·데모 필수 합격선 ≠ 95%
- WBS: 「피드백 기반 프롬프트 개선 전후 비교 **최소 1회** + 지표 보고」로 수정
- Champion/복귀 판단: **개선 비교용 Golden**, 거래 전체 정확도 **80%** 및 Rule 대비 우위

---

### 1.3 세금계산서 (Mock vs 실연동)

| 문서 | 지시 |
|---|---|
| 기획서 | **자체 Mock 필수**. 실제 팝빌 테스트망은 여유 시. `requested` / `issued` / `failed`. 실제 국세청 전송으로 표현 금지 |
| WBS 3단계 | 팝빌 **샌드박스 실데이터** 연동 |

**확정 (기획서):**
- 7주 필수 = **Popbill 규격 참고 Mock**
- 샌드박스 실연동 = **선택** (필수 QA 완료 후)
- API `nts_state`의 `issued` = **모의 완료** (실발행 아님)

---

### 1.4 카카오 채널 웹훅 / 챗봇 파싱

| 문서 | 지시 |
|---|---|
| 기획서 §4.3 | 채널 = **진입점**. 입력·확인·장부·입금·모의발행은 **전부 인앱 웹**. 채팅봇 입력·후보 자동전달은 **필수 범위 제외** |
| API · 레퍼런스 | `POST /webhook/kakao` → 내부 parse → BasicCard 가 MVP 코어처럼 기술 |

**확정 (기획서):**
- MVP 필수: 채널 **링크 → 인앱 웹** + 인앱 웹에서 입력/확인
- 웹훅으로 채팅 발화→파싱→카드: **후순위/선택** (카톡 5초 제약·공수)
- API 명세의 웹훅 절은 「선택 연동」으로 강등. 인증·서명 검증은 구현 시 유지

---

### 1.5 LLM 타임아웃 HTTP 코드

| 문서 | 지시 |
|---|---|
| 기획서 · 모델 가이드 | LLM 5초 초과 → Rule. Rule 후보 성공 시 **HTTP 200**. 타임아웃은 내부 로그 |
| API (일부) | LLM 지연 시 **HTTP 504** |

**확정 (기획서):**
| 상황 | HTTP |
|---|---|
| LLM 타임아웃 후 Rule 성공 | **200** + candidate |
| STT 등 외부 API 복구 실패 | **503** → FE 텍스트 입력 전환 (DL-33, 처음엔 504) |
| 입력/검증 오류 | **400** |
| 서버 장애 | **500** |
| 네트워크 무응답 | FE 네트워크 분기 (400 모달 금지) |

---

### 1.6 CS Soft Delete / Admin UI

| 문서 | 지시 |
|---|---|
| 기획서 | 사용자 삭제·Admin UI **제외**. CS → 본인확인 → PM 승인 → BE **검증 스크립트** + `audit_log` + Soft Delete. 입금·Mock 연결 건 Lock |
| 기능정의서 | **운영 콘솔**에서 Soft Delete |

**확정 (기획서):**
- 7주 MVP: **스크립트 Soft Delete** (콘솔 Soft Delete UI **없음**)
- 운영 콘솔을 둘 경우: **조회·모니터링·피드백 추출**까지. 삭제는 콘솔에서 막고 스크립트만
- DB에 `deleted_at` (또는 동등 Soft Delete) 필드 **필수** — 현재 DB 스키마 문서에 누락 → 보강

## 5. 타 문서 수정 지시 (체크리스트)

기획서를 고치지 않고, **하위 문서를 기획서·본 정리본에 맞출 것.**

- [ ] **WBS:** 초기 모델=클라우드 LLM(GPT-4o-mini) · 95%→Stretch · 팝빌=Mock 필수  
- [ ] **API:** 웹훅=선택 · LLM 타임아웃+Rule 성공=200 (503은 STT 등, DL-33)  
- [ ] **DB:** `deleted_at` 추가 · Payment 설명=인앱 Tab2 · fallback 의미 수정  
- [ ] **기능정의서:** Soft Delete는 콘솔이 아니라 스크립트 · 운영 콘솔 범위 축소 명시  
- [ ] **아키텍처:** 단가 null 허용 · (선택) 웹훅 경로 약화  
- [ ] **레퍼런스·디자인:** Gemma/Claude/보이스레저 표기 → 선택실험·에코빌  
- [ ] **노션:** 동일 기준으로 한 줄 공지 (이 정리본 링크)

## 6. 한 줄 결론

**에코빌 MVP = 카톡 진입 → 인앱 웹에서 음성·텍스트 → 클라우드 LLM(+Rule) → 사용자 확정 → 장부·FIFO·Mock 발행.**  
챗봇 자동파싱·로컬 Gemma 체이닝·95% 필수·팝빌 실연동·Admin Soft Delete는 **기획서상 본선이 아니다.**

`problem_fields` 표기:

- **B:** API 명세 예시처럼 필드명만 (`qty`, `amount`) — 3품목 중 어느 품목인지 알 수 없다.

`partial_candidate` (2026-09-24 추가, AI 제안 반영):

- 기획서 §7.1 「원문·수정 가능한 후보 값을 유지한 텍스트 폼에서 보완」을 위해 400 응답에 **추출된 값**을 함께 돌려준다.
- 형태는 후보와 같은 DL-01 필드(`counterparty`, `items[]`, `total_amount`, `credit`), 추출 못 한 값은 `null`. 저장하지 않으며 `entry_id`도 없다.
- `MISSING_REQUIRED_FIELD` · `AMOUNT_MISMATCH` · `AMOUNT_OUT_OF_RANGE`에서만 채운다. `EXCEED_MAX_ITEMS` · `MULTIPLE_COUNTERPARTIES_DETECTED`는 기획서 §5.1 「후보 생성 보류」에 따라 `null`, 503·500도 `null`.

```json
{
  "error_code": "MISSING_REQUIRED_FIELD",
  "message": "수량을 확인해 주세요.",
  "problem_fields": ["items[0].qty"],
  "partial_candidate": {
    "counterparty": "김씨네",
    "items": [{"name": "배추", "qty": null, "unit": null, "unit_price": null, "amount": 30000}],
```

검증 담당 경계 (AI 제안 반영, 기획서 §7 「백엔드에서 적용」과 일치):

- **AI 파서:** 발화 → 후보 JSON 추출까지. 업무 검증·HTTP 코드는 결정하지 않는다.
- **BE:** 필수값·산술·범위·품목 수 등 최종 업무 검증과 오류 응답.
- **검증 모듈은 하나:** 채점 스크립트의 「추가 확인 적합성」은 API와 같은 검증 모듈을 호출해 판정한다 (채점과 서비스 판정이 어긋나지 않도록).

**2026-09-28 회의 안건 3 확인 (전원 동의)**

3-1 `problem_fields` 규칙 — **값이 있고 서로 모순되는 필드만** 나열, `null` 필드는 넣지 않는다 (승현). FE는 나열된 칸을 모두 강조한다 — 산술 모순은 서버가 어느 값이 틀렸는지 알 수 없으므로 사용자가 고른다 (예령 질문 반영).

| 상황 | `problem_fields` |
|---|---|
| 수량 × 단가 ≠ 품목 금액 | `["items[0].qty", "items[0].unit_price", "items[0].amount"]` |
| 품목 1개·금액 `null`, 수량 × 단가 ≠ 총액 (Golden 037·039) | `["items[0].qty", "items[0].unit_price", "total_amount"]` |
| 품목 금액 합 ≠ 총액 | `["items[0].amount", "items[1].amount", "total_amount"]` |
| 필수값 누락 | 빠진 필드 (`["items[0].qty"]`, `["credit"]`) |
| 금액 범위 위반 | 범위를 벗어난 필드 |
| 품목 초과 / 다중 거래처 | `["items"]` / `["counterparty"]` |
| 입력 길이 초과 | `["utterance_text"]` |

**오류 우선순위 (2026-09-29, PM):** 한 요청에 오류가 여럿이면 코드 하나만 반환한다. `INPUT_TOO_LONG` → `MULTIPLE_COUNTERPARTIES_DETECTED` → `EXCEED_MAX_ITEMS` → `MISSING_REQUIRED_FIELD` → `AMOUNT_OUT_OF_RANGE` → `AMOUNT_MISMATCH`. 후보를 만들 수 없는 오류가 먼저, 값이 없으면 계산할 수 없으므로 누락이 범위·산술보다 먼저. `problem_fields`는 반환한 코드의 필드만.

**추가 확인 적합성 채점 (2026-09-29, D03 §0.2 ①):** 400 + Golden `expected_error_code` 일치 + 보완 필드 + 값을 지어내지 않음. `message` 문구는 채점하지 않는다.

3-2 검증 모듈 `backend/app/services/validation.py` (담당 BE, AI 리뷰). **채점 스크립트는 같은 레포 루트 `eval/`** 에 두고 `validation.py`를 직접 import한다 (`PYTHONPATH=backend python eval/score.py`). `eval/`·`data/`는 AI(김수경) 소유.

3-3 보완 제출 흐름 (승현 설계, 예령 질문 「고친 값을 어디로 다시 보내나」의 답):
- 같은 `POST /api/v1/ledger/parse`에 **`candidate` 필드**가 있으면 AI 파싱을 건너뛰고 **검증만** 한다.
- 400이면 **아무것도 저장하지 않는다.** 200일 때 비로소 후보가 저장되고 **`entry_id`** 가 내려온다 (DL-01 이름 — `candidate_id` 아님, PM 확정 2026-09-28).
- 이 경로로 저장된 후보는 **`parser_type = "manual"`** (PM 확정 2026-09-28) — AI 결과가 아니므로 「사용자 수정 전 정확도」에 섞이지 않는다. 기획서 §6.5 **수동 입력 모드**(LLM·Rule 모두 80% 미만)도 같은 경로를 쓴다.
- FE는 보완 제출마다 **새 `X-Idempotency-Key`** (같은 키·다른 본문은 409, DL-22).
- 400 `partial_candidate` 있음 → 추출값 채운 중앙 수정 모달 + `problem_fields` 강조 / 후보 없는 400 → 원문 보존 재입력 안내 / 503 → 재시도·텍스트 입력 전환 (수경). TTS 없음.
- **후속(선택):** 400 경로는 저장하지 않아 「AI가 놓친 필드」 개선 신호가 사라진다. 보완 제출이 200으로 저장될 때 원래 AI 추출값을 메타로 남기는 방안 검토 (기획서 §8.2).

#### DL-12 JWT 저장 위치 (2026-09-28 갱신)

- **A:** JWT는 localStorage(만료 24h). XSS가 한 번 뚫리면 토큰이 탈취된다.
- **B:** sessionStorage·메모리만 — 인앱 브라우저를 닫으면 재인증.
- **C (예령 제안, 추천):** **HttpOnly · Secure · SameSite=Lax 쿠키**. 자바스크립트가 토큰을 읽을 수 없어 XSS 탈취를 막는다 (OWASP Session Management Cheat Sheet).

C는 **도메인 구성에 달려 있다.** `app.<도메인>`과 `api.<도메인>`처럼 같은 사이트면 쿠키가 1st-party로 동작한다. `*.pages.dev`와 `*.up.railway.app`처럼 다른 사이트면 iOS(카톡 인앱 포함)가 쿠키를 막을 수 있어 로그인이 풀린다.

**결정 규칙 (추천):** 커스텀 도메인을 확보하면 C, 못 하면 A. BE 인증 구현(2주차 초) 전에 PM이 확정.

C를 고르면 함께 바뀌는 것:
- `docs/deploy.md` §2: `allow_credentials` **필요** (허용 origin은 FE 운영 도메인 하나, 와일드카드 불가)
- FE: 요청에 `withCredentials: true`, `Authorization` 헤더 대신 쿠키
- CSRF: `SameSite=Lax` + 상태 변경 요청의 커스텀 헤더(`X-Idempotency-Key`)로 1차 방어

### 7.3 상세 — 이관 항목의 선택지

#### DL-14 원문 `utterance_text` 저장 (D08)

DB 스키마 LedgerEntry에는 컬럼이 없고, API 응답은 원문을 돌려주며, 보안 가이드는 「AI 학습 동의자만 보관」이라고 한다.

- **B:** 동의자만 저장, 비동의자는 candidate 처리 동안만 보관 후 삭제.

기획서 §8.4가 「장부 보관과 개선 로그 보관을 구분」하라고 하므로 A가 기획서와 더 가깝다. D08에서 확정한다.
