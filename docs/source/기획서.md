## 1. 프로젝트 개요

에코빌은 현장 도소매·납품 업무를 수행하는 1인 사업자가 음성이나 일상어로 거래를 입력하면, AI가 장부 후보로 정리하고 사용자가 확인한 내용을 장부에 반영하는 서비스다.

**핵심 가치:** 카카오 인앱 웹에서 자연어로 거래를 입력하고, 구조화된 후보를 확인한 뒤 장부와 미수 관리로 연결하는 흐름을 검증한다.

카카오 채널을 서비스 진입점으로 사용하며, 거래 입력부터 후보 확인·수정·확정, 미수 조회, 입금 등록, 모의 발행 요청까지 **카카오톡 인앱 웹에서 처리**한다.

7주 프로젝트에서는 다음 흐름을 구현한다.

**카카오 채널 진입 → 인앱 웹 음성·텍스트 입력 → AI 후보 생성 → 사용자 확인·수정·확정 → 장부·미수·캘린더 반영 → 입금 시 FIFO 차감 → 별도 요청에 따른 세금계산서 모의 발행**

최초 연동은 **클라우드 STT·클라우드 구조화 LLM**으로 시작한다. LLM 타임아웃 또는 Rule 대비 평가 품질 저하에 대응하는 Champion 전환을 MVP 안전망으로 구현한다.

- **필수 실험:** 사람이 검수한 Golden Set으로 LLM·Rule을 비교하고, 사용자 수정 내용을 검토해 프롬프트·규칙 개선 전후를 최소 1회 비교한다.
- **선택 실험:** 자체 실행 SLM·하이브리드는 핵심 기능과 QA가 완료되고 시간이 남을 때만 진행한다. 미실시는 MVP 미완료 사유가 아니다.

Champion 전환·복귀의 확정 정책은 6.5와 14.2를 따른다. 정확한 모델·버전 및 남은 구현 계약은 14.2에서 관리한다.

## 2. 문제 인식과 목표 고객

### 2.1 해결하려는 문제

1인 도소매·납품 사업자는 손과 시선이 필요한 현장 업무 중 거래 직후 장부를 기록하기 어렵다. 기억이나 수기 메모에 의존해 나중에 수첩·엑셀로 옮기는 과정에서 재입력 부담과 외상 기록 누락에 따른 금전적 손실 위험이 생길 수 있다.

에코빌은 **거래와 장부 작성 사이의 시간 차이**를 줄이는 것을 목표로 한다. 카카오톡 인앱 웹의 짧은 음성·텍스트 입력을 AI가 구조화된 장부 후보로 작성하고, 사용자가 화면에서 확인·수정한 뒤 명시적으로 확정한다. 입력 부담을 낮추고 검증·사용자 확인으로 오류와 누락 위험을 줄여 장부의 신뢰성을 높인다. 사용자 확인 후에도 오류가 남을 수 있으므로 100% 신뢰성을 보장한다고 표현하지 않는다.

다만 기록 누락의 빈도, 실제 금전적 손실 규모, 기존 도구의 불편 정도는 고객 검증이 필요한 가설이다. 기존 ERP 전체가 현장 입력을 지원하지 않는다고 단정하지 않는다.

### 2.2 목표 고객

**거래 기록과 외상 정산을 직접 수행하는 1인 도소매·납품 사업자**를 대상으로 한다.

직원·관리자 권한 분리, 직원 초대, 다중 계정 공동 장부는 7주 MVP 범위에서 제외한다.

### 2.3 고객 검증 항목

- 실제 거래 표현과 기록 시점
- 외상 거래 및 부분 입금의 빈도
- 기존 기록 방식의 불편과 누락 경험
- 음성 입력 후 후보를 확인하는 과정의 수용성
- 미수 조회·캘린더의 활용도
- 초기 고객의 발행 문서 수요

**6~7주 차에 도소매 1인 사업자 등 목표 고객 5~10명 내외**를 대상으로 음성 입력과 후보 확인·수정 중심의 데모 사용성 피드백을 받는다. 위 항목은 사용 맥락을 이해하는 질문으로 활용하며, 실제 수행 과업·모집 담당·기록 양식은 검증 전에 정한다.

7주 내 지불 의사는 검증하지 않는다. 소규모 데모의 반응을 시장 전체 수요나 유료 전환율로 일반화하지 않으며, 가격·유료화 검증은 8주 차 이후로 넘긴다.

모집이 지연되어도 7주 일정을 연장하지 않는다. 기한 내 확보한 목표 고객으로 외부 사용성 테스트를 진행하고 실제 참여 인원을 보고한다. 부족한 인원을 보완하기 위한 팀 지인·내부 참여자 테스트는 내부 QA로 분리하여 보고하며, 목표 고객 검증 인원으로 합산하지 않는다.

## 3. 시장 규모와 사업 가설

### 3.1 가격 가설과 참고 계산 시나리오

시장 규모 계산에는 **Basic 월 9,900원, 부가세 포함이라는 가격 가설**을 사용한다. 확정 판매 가격이 아니다. 아래 금액은 부가세를 포함한 고객 결제액 기준의 연간 환산치이며, 부가세 제외 매출액과 구분한다.

**210만 곳은 직접 통계 근거가 확인되지 않아 핵심 시장 규모 설명에서 제외한다.** 아래 표에만 계산용 가정으로 남기며, 검증된 사업체 수나 시장 추정치로 인용하지 않는다.

| 구분 | 계산 | 연간 결제액 환산치·부가세 포함 |
|---|---|---|
| 계산용 가정: 210만 곳이 모두 구독 | 210만 곳 × 9,900원 × 12개월 | 2,494.8억 원 |
| 계산용 가정의 10%가 구독 | 21만 곳 × 9,900원 × 12개월 | 249.48억 원 |
| Basic 유료 고객 20곳 확보 시 | 20곳 × 9,900원 × 12개월 | 237.6만 원 |

이는 **사업체 수와 Basic 구독료를 적용한 결제액 환산치**이며, 실제 구매 수요가 확인된 시장 규모나 예상 매출을 의미하지 않는다. 대상 적합군의 비율과 유료 전환 가능성은 별도로 검증한다.

### 3.2 추가 검증 사항

- 통계의 기준 연도·사업체 정의와 에코빌 고객 범위의 일치 여부
- 타깃 적합군 10% 가정의 근거
- 개인 용달 운송사업자 수의 원자료와 도·소매업 대상과의 중복 여부
- 월 9,900원에 대한 지불 의사와 서비스 제공 원가 — 8주 차 이후 사업화 검토

개인 용달 운송사업자 수는 근거와 대상 적합성을 확인하기 전까지 시장 합계에 포함하지 않는다.

### 3.3 사업화 목표의 구분

고객 접촉·체험·유료 전환 목표는 **7주 개발 완료 기준과 분리**한다. 기존에 제시한 접촉 200곳, 문제 검증 100곳, 체험 40곳, 유료 고객 20곳은 후속 사업화 계획에서 실현 가능성과 추진 기간을 검토한다.

### 3.4 배경지식 및 참고자료

아래는 공식 출처와 본 프로젝트의 활용 목적이다. 제품 소개는 비교 출발점이며 실제 입력 방식·기능을 모두 검증했다는 뜻은 아니다. 모델 문서 등재는 모델 채택을 의미하지 않는다.

| 구분 | 출처 | 활용 목적·범위 |
|---|---|---|
| 시장 통계 | KOSIS 국가통계포털 | 소상공인실태조사·도소매 및 운수업 관련 통계 탐색. 기준 연도·사업체 정의·통계표 ID를 확인한 뒤 시장 산정에 사용 |
| 유사 서비스 | 장부대장 공식 소개, 한국신용데이터 캐시노트 소개 | 매출·장부 관리의 진입·입력·확인 흐름 비교. 현장 음성 입력과 외상 기록 연결의 차별점은 실제 기능 확인 후 기술 |
| 카카오 채널·챗봇 | OpenBuilder 스킬 요청·응답 JSON | 링크 버튼·SkillPayload·응답 형식 참고. 챗봇 웹훅은 선택 연동이며 현재 인앱 웹 중심 MVP의 필수 작업으로 추가하지 않음 |
| 사용자 인증 | 카카오 로그인 REST API | 인증 결과·사용자 정보 확인과 Provider ID 연결 방법 참고 |
| 모의 발행 | 팝빌 Python 전자세금계산서 발행 API | 실제 필드·응답을 참고해 자체 Mock 명세 작성. 공식 API 문서가 에코빌 자체 Mock 규격을 제공하는 것은 아님 |
| 요청·스키마 검증 | FastAPI Request Body, Pydantic Models | 입력 JSON 모델, 필수값·자료형 검사, 업무 검증 오류와 화면 안내 연결 |
| 클라우드 STT | CLOVA Speech 개요, OpenAI 음성 전사 가이드 | 음성 업로드·텍스트 반환·실패 처리의 연동 예제 확인 |
| 구조화 LLM | OpenAI Structured Outputs, Anthropic Messages API, Gemini Structured Outputs | 후보 모델의 요청·응답과 구조화 방식 확인. 동일 장부 JSON으로 연결하는 변환 계층 설계 |

KOSIS 링크는 통계 탐색 출처이며 **3장의 210만 곳을 직접 입증하는 통계표는 아직 확인 과제**다. 경쟁 서비스의 음성 입력 미지원 등 확인되지 않은 한계는 단정하지 않는다. 채택하는 예제·SDK의 버전과 재사용 조건은 실제 연동 전에 확인한다.

PM 또는 기획 담당자는 1주차 종료 전까지 확인 가능한 공식 자료로 통계와 경쟁 기능을 조사한다. 자료의 출처·확인일을 기록하고 미확인 항목은 그대로 표시한다. 개발 착수를 막는 조건으로 삼지 않는다.

### 3.5 경쟁 서비스 비교 범위

비교는 아래 세 항목으로 한정한다. 에코빌 열은 구현 완료 사실이 아닌 MVP 설계이며, 경쟁 서비스 열은 확인된 공식 근거 확보 후 갱신한다. '엑셀 집계 불가', '러닝커브 제로' 등 검증되지 않은 단정은 사용하지 않는다.

| 비교 항목 | 캐시노트 | 장부대장 | 에코빌 MVP 설계 |
|---|---|---|---|
| 거래 입력 방식 | 미확인 | 미확인 | 카카오 채널 진입 → 인앱 웹 음성·텍스트 입력 |
| 결과 확인·수정 방식 | 미확인 | 미확인 | 구조화 후보를 화면에서 확인·수정한 뒤 확정 |
| 외상·잔액 확인 방식 | 미확인 | 미확인 | 확정 외상 발생액은 캘린더, 현재 미수 잔액은 별도 조회. 입금 등록 시 FIFO 배분 |

## 4. 서비스 이용 경로와 사용자 경험

### 4.1 제품 메시지

**"말 한마디로 장부까지"**

음성으로 거래 기록을 시작할 수 있다는 가치를 전달하되, 장부 확정에는 사용자의 확인이 필요함을 명확히 한다.

### 4.2 기본 원칙

- AI 결과는 확정 전까지 장부 후보로 취급한다.
- 사용자가 확인한 거래만 장부와 미수에 반영한다.
- 모호하거나 누락된 정보는 추가 확인한다.
- 처리 상태와 실패 사유를 사용자가 이해할 수 있도록 표시한다.

### 4.3 카카오 입력·확인 경로 — 확정

카카오 채널은 서비스 진입점으로 사용한다.

다음 작업은 모두 **React 기반 카카오톡 인앱 웹**에서 수행한다.

- 음성·텍스트 입력
- 장부 후보 확인·수정·거절·확정
- 장부·미수·캘린더 조회
- 입금 등록
- 모의 발행 요청과 결과 확인

별도 채팅봇 입력·수정 흐름과 채널을 통한 후보 자동 전달은 필수 개발 범위에 포함하지 않는다.

### 4.4 선행 검증

1주차에 인앱 웹의 실제 기기 녹음·업로드 동작을 확인한다.

마이크 권한 거부 또는 STT API 타임아웃 발생 시 텍스트 입력 폼(모달 또는 화면)으로 전환하여 거래 입력을 이어갈 수 있게 한다. 이는 음성 입력 단계의 대체 경로이며, 텍스트 구조화 단계의 LLM→Rule 전환과 구분한다.

음성 기능 안정화가 지연되면 시연·배포는 텍스트 중심으로 전환한다. 음성 기능은 Beta 또는 검증된 기기·환경으로 지원 범위를 제한하고, 실제 지원 범위와 제한사항을 공개한다. 지원 기기 선정과 구체적인 공개 범위는 D10에서 정한다.

**카카오 Provider ID를 사용자 PK로 사용하고 자체 회원가입 화면은 생략한다.** 서버가 카카오 인증 결과로 사용자를 확인하는 절차는 필요하다. 인앱 웹 진입 자체나 클라이언트가 전송한 ID만으로 사용자 인증이 완료된 것으로 취급하지 않는다.

인증·세션 유지·만료·재진입 방식과 사업자별 데이터 접근 통제의 구체적 구현은 관련 DB·API·화면 개발 전에 결정한다(D07).

모든 장부·입금·피드백·모의 발행 조회와 변경 요청에서 서버가 인증된 사용자와 대상 데이터의 소유자를 대조한다. 다른 사업자의 ID로 접근했을 때 조회·변경이 거절되는지 검증한다. 고유 식별자 보유 자체를 접근 통제로 간주하지 않는다. OpenBuilder의 봇 사용자 키와 카카오 로그인 회원번호는 구분하고, 인증에 사용할 식별자 종류를 D07에 명시한다.

## 5. 7주 MVP 기능 범위

### 5.1 거래 입력과 장부 확정

**포함 범위**

- 음성·텍스트 입력과 AI 장부 후보 생성
- 후보 확인·수정·거절
- 모호한 정보의 추가 확인
- 확인한 거래의 장부 반영
- 확정 거래 조회

**확정 사항**

- **확정된 입력 범위:** 1회 입력은 거래처 1곳·최대 3품목으로 제한한다. 신규 거래처는 입력·STT 명칭을 사용하며 별칭·병합 기능은 제외한다.
- **3품목 초과:** 일부 품목을 임의로 잘라 저장하지 않고 후보 생성을 보류하며 HTTP 400을 반환한다. 화면 중앙의 텍스트 모달에 "최대 3개까지만 입력 가능합니다. 나누어 입력해 주세요"라고 안내한다. 오류 음성(TTS) 출력은 MVP에서 전면 제외한다.
- **다중 거래처:** 여러 거래처가 감지되면 실패 처리하고 거래처별로 나누어 입력하도록 안내한다.
- **단가 생략 허용:** 단가가 없는 입력은 `unit_price: null`로 파싱한다. 해당 단가를 사용하는 곱셈 검증만 생략하고 필수값·자료형·금액 범위 검증과 사용자 확인은 유지한다. 화면에 거래 총액을 명확히 표시한다.
- **품목 금액 합계:** 모든 품목의 금액이 제공된 경우, 단가 유무와 관계없이 품목 금액 합계와 거래 총액을 반드시 대조한다. 일부 품목 금액이 없으면 값을 추정해 채우거나 부분 합계를 전체 총액과 비교하지 않는다.
- **수량 누락:** AI가 임의로 1을 넣지 않는다. 필수값 누락으로 처리하고 사용자에게 해당 필드 보완을 요청한다.
- **선택 필드:** 단위·단가·품목별 금액이 입력에 없으면 생략 또는 `null`로 처리하며 AI가 임의 추정하지 않는다. 단가는 위 `unit_price: null` 규격을 따른다.
- **단가가 있는 경우:** 백엔드에서 수량×단가와 금액의 일치 여부를 검증하고, 불일치 시 HTTP 400 응답으로 사용자 확인을 요청한다.
- **정정 UI 범위:** 사용자용 확정 거래 정정·삭제·재입력 UI와 CS용 Admin UI는 MVP에서 전면 제외한다. 일정 여유에 따른 선택 구현도 포함하지 않는다. 확정 전 후보 수정 화면은 유지한다.

다음 세부사항은 D04·D06에서 결정한다.

- 동일 거래처에 대한 한 번의 입력에서 허용할 거래 수와 다중 거래처 오류 응답 규격
- 신규 거래처의 생성 시점과 동명 거래처 식별
- 금액 허용 범위의 구체값과 필수값 보완 오류 JSON
- 수량 단위, 금액 계산 및 반올림 기준
- 현금·외상 거래의 입력 범위
- 확정된 CS 처리 정책의 스크립트·감사 로그·동시성 제어 세부 계약

### 5.2 미수금 캘린더 및 입금·잔액 처리

**확정 사항**

| 항목 | 적용 범위 |
|---|---|
| 캘린더 | 등록일별 거래처명과 확정 외상 발생액 합계 표시 |
| 미수 조회 | 입금 반영 후 남은 미수 잔액을 별도로 표시 |
| 부분 입금 | 같은 거래처의 오래된 외상 건부터 FIFO 자동 차감 |
| 등록일 | 최초 입력 요청을 서버가 수신한 시각 `created_at`의 날짜 |
| FIFO 정렬 | 확정 외상 건의 `created_at` 오름차순, 동일 시각에는 Auto Increment PK 오름차순 |
| 초과 입금 | 오류 응답으로 차단 |
| 입금 취소·정정 UI | 7주 MVP에서 제외 |
| 기존 잔액 | 도입 이전 잔액의 입력·가져오기 제외 |
| 추적 대상 | 에코빌에서 신규 생성되고 확정된 거래 |

캘린더는 **유효한 확정 거래의 외상 발생액**을 표시한다. 입금으로 미수 잔액이 줄어들어도 해당 발생액은 감소하지 않는다. 다만 오류 거래를 승인된 절차로 Soft Delete하면 해당 거래는 집계에서 제외한다. 이는 입금에 따른 잔액 감소와 구분한다.

**검토 항목**

- 저장 시간대와 캘린더 날짜의 표시 기준
- 동일 요청 재전송 시 최초 `created_at`과 거래 식별자를 유지하는 방법
- 오래된 후보가 입금 이후 늦게 확정될 때 기존 FIFO 배분에 미치는 영향
- CS 스크립트의 실행 전후 확인·실패 대응 및 입금·발행 동시 요청과의 충돌 방지

**CS 처리 정책 — 확정: 기술적 격리와 제한적 수동 처리**

- 카카오 채널로 접수한 CS 요청의 본인과 데이터 소유권을 검증된 Provider ID로 확인한다. 사용자가 ID 문자열을 알려주는 것만으로 본인 확인을 대신하지 않는다.
- 본인·소유권 확인 후 **PM의 승인을 거쳐 백엔드 담당자만** 미리 검증된 내부 스크립트로 Soft Delete한다. 실행 대상은 입금·모의 발행 연결 이력이 없는 거래로 제한한다. 물리 삭제·임의 SQL 보정은 수행하지 않으며 사용자용 삭제 화면과 Admin UI는 만들지 않는다.
- 변경 사유·거래 ID·변경 전후 데이터·실행자·시각을 `audit_log`에 남긴다. 이는 후보 수정 피드백을 저장하는 `FeedbackEvent`와 구분한다.
- 장부·캘린더·미수 조회 및 관련 집계는 `deleted_at IS NULL`인 유효 거래만 대상으로 한다. 삭제된 거래가 FIFO 배분·모의 발행 대상에 다시 포함되지 않도록 검증한다.
- **Lock 조건:** 부분·전액 입금 또는 모의 세금계산서 이력이 연결된 거래는 CS 수동 Soft Delete·복구 대상에서도 제외한다. 개발팀의 예외적인 직접 보정 경로를 MVP에 두지 않는다. 발행 완료 여부와 무관하게 연결 이력 존재 여부로 차단한다.
- 사용 제한 안내에는 "입금 또는 모의 발행 이력이 연결된 거래는 MVP에서 정정·삭제할 수 없습니다"를 명시한다.

스크립트의 실행 전후 검증·실패 시 원상 복원, `audit_log` 상세 구조, 연결 이력 확인과 변경의 동시성 제어는 D06에서 구현 전에 정한다. 처리 불가 거래를 복구 가능하다고 안내하지 않으며, 이 제한을 실제 사용 전에 고지한다.

### 5.3 세금계산서 모의 발행 — 확정

- 팝빌의 공식 API 규격을 참고하여 **백엔드 자체 Mock API**를 구현한다.
- 문서는 **과세 전자세금계산서**로 한정한다.
- 모의 발행 요청·상태 조회·실패 안내를 연결한다.
- 화면과 데모에 모의 발행임을 표시한다.
- 실제 발행이나 국세청 전송이 완료된 것으로 표현하지 않는다.

면세 계산서, 거래명세서, 영수증은 MVP에서 제외한다.

실제 팝빌 테스트망 연결과 인증 준비는 필수 기능 및 QA가 완료되고 시간이 남을 경우에만 진행한다. 실제 발행·국세청 전송으로 전환하는 일정은 Mock 코어 검증 후 후속 사업화 단계에서 정한다.

## 6. AI 모델 선정과 실험 계획

### 6.1 모델 선정 상태

**최초 연동은 개발 공수가 적은 클라우드 STT와 클라우드 LLM으로 확정한다.** 각각 1개 모델로 기본 경로를 시작하며 정확한 제품·버전은 D01에서 결정한다.

CLOVA Speech·Whisper·GPT-4o-mini 등은 팀이 제시한 예시이며 채택이 확정된 제품이 아니다. 연동 시점의 제공 여부·권한·실행 조건을 확인한다. 자체 실행 SLM은 핵심 기능과 QA 완료 후 여유가 있을 때만 테스트한다.

최종 채택 모델은 **1~3주차 초기 기준선 측정 결과를 근거로 판단**한다. 개발을 시작할 최초 모델은 먼저 정하되, 최종 선택은 같은 개발용 Golden Set에서 확인한 정확도·속도·비용을 바탕으로 한다. STT 비교에는 동일한 음성 입력을 사용한다. 모델을 사전에 단정하는 대신 실측으로 선택 근거를 확보하며, 로컬 비교는 기존 선택 과제 범위에서만 수행한다.

### 6.2 선정 기준

| 영역 | 확인할 내용 |
|---|---|
| STT | 한국어 거래 표현, 숫자·단위·품목 인식, 소음 환경, 지연과 비용 |
| 구조화 | 거래처·품목·수량·금액 추출, 다중 품목 처리, 누락·모호성 대응 |
| 출력 형식 | 정의한 JSON 스키마 준수와 오류 처리 |
| 운영 | 응답 시간, 재시도 포함 처리 비용, 배포·유지보수 부담 |
| 데이터 처리 | 외부 전송 범위, 저장 정책과 운영 제약 |

### 6.3 비교 범위와 실험 중단 기준

실험은 **사람이 100% 검수한 Golden Set 전체 50~100건** 범위로 제한한다. 개발 비교용과 최종 확인용의 합계이며 각각 50~100건을 확보한다는 뜻이 아니다. 반복 비교에는 개발용 Golden Set을 사용한다.

핵심 판단 지표는 **금액 Exact Match와 필수 필드 F1 Score**다. 응답시간·실험 중 확인 가능한 호출 비용·실패 사례는 보조 기록으로 남기되, 전용 수익성 측정 시스템은 개발하지 않는다.

평가 결과가 좋지 않거나 실험으로 개발 일정이 1주 이상 지연되면 추가 모델 탐색을 중단한다. 운영 파서는 6.5의 80%·상대 품질 기준에 따라 선택하며 LLM·Rule 모두 80% 미만이면 수동 입력으로 전환한다. 상대 품질 지표가 엇갈릴 때의 판정식과 지연 판단의 기준 일정은 첫 비교 전에 PM이 확정한다(D02·D03).

중단 대상은 추가 모델 탐색이다. 모델 탐색을 중단해도 사용자 피드백 기반 프롬프트 개선과 동일 Golden Set에서의 개선 전후 비교 최소 1회는 반드시 수행한다.

자체 실행 SLM·하이브리드 비교는 선택 과제다. 수행할 경우에만 품질·지연·비용·운영 부담을 비교하고, 성능 향상이나 비용 절감을 사전에 단정하지 않는다.

### 6.4 실험 절차

1. 후보 모델의 사용 가능성과 실행 조건을 확인한다.
2. AI 담당자가 제안하고 PM이 기준 모델과 평가 조건을 결정한다.
3. 개발용 Golden Set의 동일 입력·스키마·채점 기준으로 LLM과 Rule 결과를 측정한다.
4. 오류를 분석하고 프롬프트·규칙 개선 전후를 비교한다.
5. 실험 중단 기준과 평가 결과에 따라 적용 모델을 고정하고, 최종 확인용 Golden Set으로 결과를 보고한다.

STT 비교와 텍스트 구조화 비교를 분리하고, 실제 음성을 입력하는 전체 흐름도 별도로 확인한다.

### 6.5 오류 방어와의 구분

하이브리드 구성은 모델의 역할을 나누는 방법이고, 오류 방어는 결과를 검증하는 절차다.

정규식·스키마 검사·산술 검증은 일부 형식 및 계산 오류를 찾는 데 사용한다. **모든 금액 오류나 의미 오류를 검출할 수 있다고 주장하지 않는다.**

**Champion 교체 정책 — D02 최종 확정**

- **요청별 시간 제한:** LLM 구조화 API 호출 대기는 최대 5초다. 초과 시 해당 호출의 대기를 중단하고 내부 Rule 파서로 넘긴다. 이 5초는 STT·Rule·전체 요청 시간을 포함하지 않는다.
- **정확도 기준:** 동일한 개선 비교용 Golden Set 중 `정상 구조화 가능` 사례에서 필수 필드 5종 기반 거래 전체 정확도를 측정한다. 실시간 개별 입력의 정답을 추정하는 방식이 아니다.
- **Rule 전환:** LLM 거래 전체 정확도가 80% 미만이거나, 금액 Exact Match·필수 필드 F1 비교에서 Rule 대비 품질 저하로 판정되면 LLM 호출을 일시 중단하고 전체 자동 파싱 요청을 Rule로 전환한다. 장부 조회·입금 등 다른 기능의 트래픽을 뜻하지 않는다.
- **수동 모드 전환:** LLM과 Rule 모두 위 정확도가 80% 미만이면 자동 파싱을 전면 중단한다. 서비스 진입부터 거래처·품목·수량·총액·외상 여부를 직접 입력하는 구조화된 수동 폼을 제공한다. 자유문장을 입력한 뒤 같은 AI를 다시 호출하는 방식이 아니다.
- **개별 실패:** 운영 파서의 정확도가 80% 이상이어도 특정 요청에서 적용 가능한 Rule 처리 후 필수값 누락·산술 모순이 남으면 해당 요청만 HTTP 400으로 수동 보완에 연결한다.
- **LLM 복귀:** 프롬프트 개선 후 동일한 개선 비교용 Golden Set에서 거래 전체 정확도 80% 이상과 Rule 대비 품질 우위를 모두 확인하고, PM(최승현)의 명시적 승인으로 백엔드에서 LLM 경로를 수동 복구한다. 자동 복귀하지 않는다.
- **데이터 격리:** 최종 평가용 Golden Set은 모델 선택·전환·복귀 판단에 사용하지 않고 최종 성능 보고에만 사용한다.

수동 폼도 백엔드 검증과 사용자 확정 후에만 장부에 반영한다. 서버 자체 장애가 발생한 경우 수동 폼이 저장 성공을 보장하지 않는다. 상대 품질 지표가 엇갈릴 때의 판정식, 점검 주기, Rule 지원 범위 및 수동 모드에서 Rule 단독 재개 절차 등 미확정 운영 세부사항은 14.2에 구분한다. 로컬·클라우드 하이브리드 라우팅은 선택 실험 범위로 유지한다.

## 7. 오류 처리와 데이터 일관성

아래 규칙은 LLM·Rule의 선택과 무관하게 백엔드에서 적용한다. 정상적으로 구조화된 AI 결과는 항상 `candidate`로 저장하며 사용자 [확정] 요청과 검증을 통과해야 `confirmed`로 전이한다. `candidate`·`rejected`는 장부 집계·미수·FIFO 배분에서 제외한다. JSON 변환 자체가 실패한 응답을 정상 후보로 간주하지 않는다.

### 7.1 AI 결과 검증

- 필수 항목과 자료형을 검사한다.
- 계산 가능한 항목은 수량·단가·합계 관계를 검증한다.
- 불명확한 값은 임의로 확정하지 않고 사용자에게 확인한다.
- 검증을 통과한 결과도 사용자 확인 전에는 장부에 반영하지 않는다.

필수 업무 정보 누락·모순 또는 적용 대상 계산의 불일치는 HTTP 400과 문제 필드·사유를 설명하는 텍스트 메시지로 사용자 보완을 요청한다. 프론트엔드는 화면 중앙의 텍스트 모달로 안내하고, 원문·수정 가능한 후보 값을 유지한 텍스트 폼에서 보완하도록 한다. 오류 TTS는 구현하지 않는다.

단가가 있으면 수량×단가 검증을 수행하고, 단가가 없으면 해당 곱셈 검증만 생략한다. 모든 품목 금액이 제공되면 그 합계와 거래 총액을 대조한다. 필수값·자료형·금액 범위 검증은 항상 유지하며 수량 누락을 임의의 1로 보완하지 않는다. 선택 필드가 잘못 생성되어 산술 모순이 발생한 경우에도 HTTP 400으로 확정 전 보완을 요구한다.

위 HTTP 400 규칙은 사용자 입력·업무 검증 오류에 적용한다. 인증·권한 오류나 서버·외부 API 장애를 입력 오류로 일괄 변환하지 않으며, 해당 오류 계약은 D07·D09에서 구분한다. 마이크 권한 거부는 프론트엔드에서 안내하고 STT 타임아웃은 4.4의 텍스트 입력 전환을 적용한다.

**최종 응답과 내부 오류의 구분 — 확정**

| 상황 | 최종 응답·프론트엔드 처리 |
|---|---|
| LLM 5초 초과 후 Rule 후보 생성 성공 | HTTP 200으로 후보 표시. LLM 타임아웃은 내부 로그로 기록하며 최종 실패로 반환하지 않음 |
| 활성 경로와 적용 가능한 폴백 이후 필수값 누락·산술 모순 | HTTP 400과 문제 필드·사유 반환. 입력 수정 텍스트 모달 후 해당 건의 수동 보완 |
| STT 등 복구되지 않은 외부 서비스 타임아웃 | HTTP 504와 오류 유형 반환. STT 오류이면 자연어 텍스트 입력창으로 전환 |
| 응답 가능한 서버 내부 장애 | HTTP 500과 오류 유형 반환, 시스템 장애로 안내. 사용자 입력 오류로 변환하지 않음 |
| 서버 무응답·네트워크 실패·오류 본문 없음 | 프론트엔드의 별도 네트워크 예외 분기로 처리. 400 수정 모달로 오인하지 않고 저장·확정 성공으로 간주하지 않음 |

LLM+Rule 모드와 Rule 단독 모드 모두 동일한 최종 입력 검증 원칙을 적용한다. 품목 초과 등 입력 범위 위반은 기존대로 400으로 거절한다. 인증·권한 오류는 별도 규격을 유지한다. 오류 유형의 구체적인 JSON 키·값과 프론트엔드 분기 계약은 D09에서 정한다.

### 7.2 상태 저장과 중복 반영 방지

모바일 화면 이탈·새로고침 이후에도 처리 결과를 확인할 수 있도록 백엔드에 필요한 상태와 결과를 저장한다.

- 같은 요청의 상태를 다시 조회할 수 있도록 한다.
- 중복 요청으로 거래·입금·모의 발행이 중복 반영되지 않도록 한다.
- 시간 초과를 즉시 실패로 단정하지 않는다.
- 결과가 불명확하면 **'결과 확인 중'**으로 안내한다.

고유 요청 키(UUID)는 **프롬프트나 LLM이 아닌 애플리케이션에서 생성**한다. 동일 작업의 버튼 연타·네트워크 재전송에는 같은 키를 재사용한다. 장부 생성·확정, 입금, 모의 발행 각각에서 서버가 사용자·작업·요청 키를 기준으로 이미 처리한 작업인지 확인한다.

UUID 생성만으로 중복이 방지되는 것은 아니다. 동시 요청에서도 업무 변경과 처리 기록이 한 번만 반영되도록 서버 저장·처리를 구성한다. 생성 위치(클라이언트/서버), 키 전달·저장, 같은 키에 다른 내용이 들어온 경우의 처리, 동시성 제어 방식은 API 구현 전에 확정한다. 같은 문장을 새 거래로 입력하는 경우와 기존 요청의 재전송을 구분한다.

### 7.3 모의 발행 연동 구조

발행 요청·상태 조회 기능은 외부 연동 부분과 분리하여, 이후 실제 API로 교체할 수 있도록 설계한다.

발행 범위는 **5.3**, 검증 시나리오는 **9장**을 기준으로 한다.

### 7.4 공식 예제·코드 활용 계획

| 참고 코드 | 적용 대상 | 수정·검증할 내용 |
|---|---|---|
| 3.4의 FastAPI·Pydantic 공식 예제 | 장부 입력·후보 검증 모델 | 거래처·품목 배열·금액·외상 여부 필드와 3품목 제한을 프로젝트 규격에 맞춤. 산술·업무 오류는 별도 검사하고 사용자 보완 응답과 연결 |
| STT·구조화 모델 공식 요청 예제 | 음성 전사·후보 생성 모듈 | 인증정보는 서버에서 관리하고 모델 응답을 공통 JSON으로 변환. STT 실패는 텍스트 입력 전환, LLM 5초 타임아웃은 Rule 전환으로 분리 |
| 팝빌 발행 공식 예제 | 자체 Mock 요청·응답 정의 | 참고 필드와 생략 필드를 명시하고 네트워크 발행 호출 대신 3상태 가상 응답 구현 |
| OpenBuilder JSON 예제 | 선택 챗봇 연동 검토 | 웹훅을 추가하기로 결정한 경우에만 사용. 예제에 사용자 식별값이 있다는 이유로 웹 인증을 생략하지 않음 |

이는 코드 확보·활용 계획이며 실행 검증 완료를 뜻하지 않는다. 예제 채택 시 출처·버전·변경 내용을 남기고 정상·누락·불일치 사례로 확인한다.

## 8. 평가 데이터와 피드백 개선 계획

### 8.1 데이터 구분

| 데이터 | 용도 |
|---|---|
| `Seed Set` | 학습·프롬프트 예시 작성, 규칙 개발, 오류 분석 |
| 개발용 `Golden Set` | 모델 비교와 개선 전후 반복 평가 |
| 최종 `Golden Set` | 개발·튜닝에 사용하지 않는 최종 성능 확인 |
| 피드백 로그 | 사용자 수정·거절 사례의 검토와 개선 후보 수집 |

**Seed Set은 200~500건, Golden Set은 개선 비교용(개발용)·최종 평가용 합계 50~100건**으로 구축한다. Golden Set은 사람이 100% 검수한다. 총량을 늘리거나 최종 평가용만 50~100건을 확보하는 것이 아니다.

**D03 확정:** 최종 평가용으로 분리한 Set 내부에만 명확한 표현 60%·복잡/생략 표현 40%(6:4)를 적용한다. 이는 초기 테스트의 표현 난이도 구성이지 실제 현장 분포나 객관성을 보장하는 수치가 아니다. 개선 비교용과 최종 평가용 사이의 분할 비율을 뜻하지도 않는다. 정확한 건수·두 세트 분할·정수 배분 방식은 구축 전에 정한다.

표현 난이도와 별도로 각 사례에 `정상 구조화 가능` 또는 `추가 확인 필요`라는 기대 결과 라벨을 부여한다. 사투리·조사 생략·단가 생략이 있어도 필수 정보가 모두 있으면 정상 구조화 가능이다. 'A상사에 사과 2박스 단가 3만 원, 총 6만 원 외상 달아줘'는 정상 사례이며, '사과랑 배 합쳐서 10만 원'은 거래처·수량·외상 여부가 부족한 추가 확인 사례다. 6:4를 정상 처리·추가 확인 사례 비율로 해석하지 않는다.

초기 구축은 합성 데이터 중심으로 시작한다. **출시 후 평가셋의 확대 규모와 실제 사례 비중**은 동의받은 발화·수정 로그의 유입량과 검수 여력을 본 뒤 정한다. 단, MVP에서 비교에 사용할 Golden Set은 위 범위 안에서 평가 전에 고정하며, 후속 데이터는 별도 버전으로 관리한다. 실제 음성 비중을 추후 검토한다는 이유로 원본 오디오 삭제 원칙을 바꾸지는 않는다. 음성 샘플 보관이 필요하면 그 목적·동의·보관 조건을 수집 전에 별도로 결정한다.

초기에는 팀의 도메인 지식을 바탕으로 거래 템플릿을 직접 작성하고 합성·변형한다. 숫자 표기, 순서 변경, 방언·구어체, 생략, 수정 발화, 1~3품목을 포함한다. AI·데이터 담당자가 원문·정답 초안을 작성하고 PM이 업무 의미와 정답을 검수한다. 사람 검수는 정답 품질 확인이며, 합성 데이터를 실제 현장 데이터로 바꾸는 것은 아니다.

출시 후에는 개선 활용에 동의한 수정 피드백을 검토하여 Seed를 보강한다. 사용자 수정이 실제 거래 변경인지 AI 오류 정정인지 확인한 뒤 편입한다. 실제 사례로 Golden을 확장할 때도 별도 검수·중복 확인·새 버전 발행을 거치며, Seed·프롬프트 예시로 사용한 사례를 독립 평가에 재사용하지 않는다.

문장만 조금 바꾼 동일 거래 유형이 서로 다른 세트에 섞이지 않도록 분리 기준을 정한다.

분할은 원본 사례·템플릿과 파생 문장 그룹 단위로 수행한다. Golden의 문장·정답을 학습·프롬프트 예시로 넣지 않는다. 개발용 Golden의 점수·오류 유형은 반복 개선에 활용할 수 있으나, 그 결과는 독립 최종 성능과 구분한다.

최종 `Golden Set`을 보고 수정했다면, 해당 평가 결과를 독립적인 최종 성능으로 제시하지 않는다.

최종 평가용 Golden Set은 모델 선택·프롬프트 개선·Champion 복귀 판단에 재사용하지 않는다. 반복 개선과 운영 모드 판단에는 개선 비교용 Golden Set만 사용한다.

**데이터셋 레코드 구조**

| 필드 | 형태 | 의미 |
|---|---|---|
| `utterance_text` | String | 가명 처리한 원문 또는 STT 텍스트 |
| `expected_json` | JSON Object | 거래처·품목별 수량·단위·금액·외상 여부 등 정답 |
| 표현 난이도 | 라벨 | 명확한 표현 / 복잡·생략 표현. 기대 결과 라벨과 독립적으로 관리 |
| 기대 결과 | 라벨 | 정상 구조화 가능 / 추가 확인 필요 |
| 보완 필요 필드 | 필드 목록 | 추가 확인 사례에서 실제 누락·모순으로 확인해야 할 항목. 임의 값을 정답으로 채우지 않음 |
| `review_status` | 상태값 | 미검수·검수 완료·재검토 여부. Golden에는 검수 완료만 편입 |
| 분할·출처 정보 | 메타데이터 | Seed/개발 Golden/최종 Golden, 합성/직접 작성/피드백 구분 |
| 원본 그룹·버전·검수 이력 | 메타데이터 | 파생 문장 간 누출 방지, 정답 변경 및 검수 추적 |

아래는 명확한 단일 품목 사례의 **형태 예시**다. 단가 누락·소수 수량·필수값 범위의 최종 API 계약은 D03·D04에서 정한다.

```json
{
  "utterance_text": "A상사 사과 5박스, 박스당 16000원, 총 80000원 외상",
  "expected_json": {
    "counterparty": "A상사",
    "items": [
      {"name": "사과", "qty": 5, "unit": "박스", "unit_price_krw": 16000, "amount_krw": 80000}
    ],
    "total_amount_krw": 80000,
    "credit": true
  },
  "review_status": "reviewed"
}
```

예시의 `reviewed`는 형식 설명이며 실제 검수 데이터가 확보됐다는 의미가 아니다. 모호한 입력은 임의 정답을 채우지 않고 확인이 필요한 항목을 별도 정답 정보로 기록한다.

### 8.2 피드백 반영 전후 비교 사이클

기존 제안서의 개선 사이클을 다음과 같이 유지한다.

**사용자 수정·거절 로그 수집 → 오류 원인 검토 → 프롬프트·규칙 개선 → 동일 개발용 Golden Set으로 전후 비교 → 결과 기록**

최소 1회의 비교 사이클을 계획에 포함한다. 개선한 사례뿐 아니라 새롭게 발생한 오류와 기존 성능의 저하 여부도 확인한다.

사용자의 수정 내용을 곧바로 학습 정답으로 사용하지 않고, 거래 내용 변경인지 AI 오류 수정인지 검토한다.

파인튜닝은 필수가 아니다. **성능 향상 자체를 보장하지 않고, 개선 시도와 비교 결과를 산출물로 남긴다.**

### 8.3 정확도 95%의 상태와 평가 기준

**95%는 연구 목표(Stretch Goal)이며 배포 필수 합격선이 아니다.** 85~90%는 팀이 제시한 예시이며 새로운 합격선이나 이미 달성한 성능을 의미하지 않는다. 사용자 수정·확정 기능을 포함해 7주 차 데모·배포를 추진한다.

모델 비교의 핵심 지표는 금액 Exact Match·필수 필드 F1이다. **95% 연구 목표의 대상은 사용자 수정 전 거래 전체 정확도로 확정한다.** 지표별 분모와 의미를 혼용하지 않는다.

거래 전체 정답 판정의 필수 필드는 **거래처·품목명·수량·거래 총액·외상 여부**다. 단위·단가·품목별 금액은 선택 필드로, 생략되어도 필수 필드가 모두 맞으면 거래 전체 정답으로 인정한다. 원문과 다르거나 근거 없이 생성된 선택 필드는 **선택 필드 오류(False Positive) 건수**로 별도 보고한다. 이 오류를 필수 필드 기반 거래 전체 정확도에 직접 합산하지 않으며, 산술 모순이 있으면 서비스에서는 확정 전에 HTTP 400으로 보완을 요구한다.

평가의 '정답 판정'과 서비스의 '확정 허용'은 구분한다. 필수 필드가 맞더라도 검증 오류가 있는 후보는 확정할 수 없으며, 필수 필드 평가 결과가 좋아도 선택 필드 오류를 누락하지 않는다. 95%의 지위는 연구 목표로 유지하고 새 배포 합격선을 도입하지 않는다.

LLM과 Rule은 동일한 Golden Set을 기대 결과 라벨별로 비교한다. 정상 구조화 가능 사례에서 Rule이 처리하지 못한 건도 거래 전체 정확도 분모에 포함하여 실패·미지원으로 집계한다. 추가 확인 필요 사례의 적절한 보완 요청은 별도 트랙의 정답이다. Rule 지원 범위 내 성능은 보조 지표로만 보고한다.

거래 전체 정확도는 다음 원칙으로 측정한다.

> `정상 구조화 가능` 라벨의 전체 건수 중, 사용자 수정 전 후보의 필수 필드 5종이 모두 정답과 일치한 건수의 비율을 거래 전체 정확도로 계산한다. 표현이 복잡해도 정보가 충분하면 포함한다. 생성 실패와 불필요한 추가 확인은 오답이다. 80% 운영 기준과 95% 연구 목표는 이 지표를 사용하되, 운영 전환 판단에는 개선 비교용 Golden Set만 사용한다.

확정이 필요한 사항은 다음과 같다.

- 범위 내 정확한 데이터 건수·개선 비교용/최종 평가용 분할·최종 평가용 6:4의 정수 배분
- 표현 난이도·기대 결과 라벨의 검수 체크리스트와 각 트랙의 사례 수
- 확정된 필수 필드의 정규화 기준과 선택 필드 오류의 품목·필드별 집계 규칙
- 품목 대응·누락·추가 예측 처리와 F1 평균 방식
- 반복 실행 방법과 실험 종료 일정

거래 전체 정확도, 필드별 정확도, 모호한 입력의 추가 확인 성능, 음성부터 장부까지의 결과는 구분하여 보고한다.

**정량 평가 정의**

| 지표 | 측정·계산 방식 | 보고 원칙 |
|---|---|---|
| 거래 전체 정확도 | 정상 구조화 가능 사례 중 사용자 수정 전 필수 필드 5종이 모두 일치한 건수 / 정상 구조화 가능 사례 수 | 실패·Rule 미지원·불필요한 추가 확인은 오답. 정답 건수와 분모를 함께 보고 |
| 추가 확인 적합성 | 추가 확인 필요 사례 중 값을 지어내지 않고 실제 누락·모순 필드의 보완을 요청한 건수 / 추가 확인 필요 사례 수 | 백엔드 HTTP 400과 적절한 보완 안내를 확인. 무관한 400·시스템 장애는 정답 아님. 거래 전체 정확도와 분리 보고 |
| 필드별 정확도 | 해당 정답 필드가 존재하는 평가 대상 중 정규화 후 정확히 일치한 수 / 해당 평가 대상 수 | 누락은 오답. 거래처·품목·수량·단위·금액·외상 여부별 보고, 불필요하게 생성한 값은 F1과 별도 오류로 집계 |
| 필수 필드 F1 | Precision=TP/(TP+FP), Recall=TP/(TP+FN), F1=2TP/(2TP+FP+FN) | 일치 필드값을 TP, 잘못되거나 추가된 예측을 FP, 누락되거나 맞히지 못한 정답을 FN으로 집계. 품목 대응·평균·분모 0 처리는 D03에서 고정 |
| 금액 Exact Match | 총액 정답이 있는 대상 중 후보 총액이 정확히 일치한 건수 / 총액 정답이 있는 평가 건수 | 생성 실패·금액 누락도 분모에 포함. 품목별 금액 일치는 별도 보고 |
| 응답시간 p50·p95 | 서버가 입력 요청을 수신한 때부터 후보 또는 최종 오류 응답을 반환할 때까지의 시간 분포 | 음성·텍스트 구분, STT·재시도 포함 여부 명시. 성공·실패 건수와 실패 지연 별도 보고. 사용자 녹음·확인 시간과 구분 |
| 미수·FIFO 불일치 건수 | 수작업 정답 시나리오와 비교해 배분 순서·거래별 잔액·거래처 합계가 다른 사례 수 | 0건 목표. 테스트 사례 수·조건 함께 기록 |
| 중복 반영 건수 | 동일 요청 키의 재전송·동시 요청으로 한 작업이 두 번 이상 반영된 사례 수 | 장부·입금·Mock 각각 0건 목표. 새 거래 입력과 구분 |

1~3주차 연동·기준선 측정에서 응답시간과 파서 성능을 기록한다. LLM 호출 대기 5초와 정확도 80% 전환 기준은 확정값으로 적용하며, 전체 응답시간 목표는 실측 후 정한다. 85~90%를 새 배포 합격선으로 도입하지 않는다. 모델·프롬프트·데이터·채점 버전, 라벨별 평가 건수, 실패 수, 실행 조건을 결과와 함께 보관한다.

응답시간·건당 비용의 목표값은 개발 전에 임의로 정하지 않는다. 초기 기준선과 모델 선정 후 실측 결과를 바탕으로 목표를 정하고, 후반부 사용성 테스트에서 체감 대기·수정 부담을 확인한다. 비용 측정에는 STT·LLM 호출·재시도 등 포함 범위를 명시한다. 월 9,900원 가격 가설과의 원가·마진 검토는 후속 사업화에서 수행한다.

95%는 이미 연구 목표로 정해졌으므로 합격선 여부를 다시 미정으로 돌리지 않는다. 85~90%에서도 사용자가 큰 불편 없이 수정할 수 있다면 빠른 배포와 피드백 수집을 우선한다는 의견은 이 방향을 보완한다. 수치 자체를 새 합격선으로 지정하지 않으며 기능 검증은 별도로 유지한다.

#### 8.3.1 정성 평가 — 사용성 관찰

6~7주차 목표 고객 5~10명 내외에게 **음성으로 거래 입력 → 후보 확인 → 미리 준비한 오류 수정 → 장부 확정** 과업을 수행하도록 한다. 미수 조회·입금 결과 이해도도 함께 확인한다.

음성 지원이 제한되면 텍스트 입력 과업으로 전환하고 실제 입력 방식을 기록한다. 모집 미달 시에도 7주 내 확보한 목표 고객으로 진행하며, 외부 사용성 결과와 팀 지인·내부 QA 결과를 구분하여 인원·조건·한계를 보고한다.

- 관찰: 과업 완료 여부, 조작을 멈춘 지점과 횟수, 도움 요청, 수정·재입력 발생 지점과 이유.
- 인터뷰: 기존 기록 방식의 재입력 부담, 화면 확인·수정의 이해도, 현장에서 사용하기 어려운 상황과 개선 요구.
- 기록: 참여자를 가명으로 구분하고 기기·과업·도움 제공 여부와 관찰 사실·사용자 의견을 분리하여 정리.

재입력 부담 감소는 참여자의 주관적 평가로 보고한다. 실제 시간 단축을 주장하려면 기존 방식과 같은 과업 조건의 비교 측정이 필요하다. 조작 중단의 구체적 집계 규칙·질문지·모집 일정은 D11에서 테스트 전에 고정한다.

### 8.4 데이터 보관

원본 오디오는 STT 텍스트 변환 직후 삭제한다. 실패·시간 초과 시 메모리·임시 파일 정리와 외부 STT의 데이터 처리 조건은 실제 음성 수집 전에 확인한다(D08).

개선용 데이터는 서비스 개선에 동의받은 `FeedbackEvent` 텍스트 수정 로그를 대상으로 한다. `corrected_data`는 JSON Object 단일 필드로 저장한다. 서비스 제공을 위한 장부 보관과 개선 실험용 로그 보관은 구분한다.

개선용 피드백 수집을 시작하기 전에 활용 목적·대상·보관·삭제 조건을 안내하고 동의를 기록한다. Seed·Golden 편입 전에는 원문과 수정 JSON 모두에서 실명·연락처 등 식별 정보를 가명 처리하거나 제거한다. 가명 처리 후에도 접근 범위를 제한한다. 입력 텍스트 전체를 AI 개선에 사용하는 범위 확대는 이번 확정 사항에 포함하지 않는다.

팀은 수정 로그의 영구 보관을 제안했으나, 보관 목적·대상·종료 조건·동의 철회·삭제 요청 처리까지 정해진 것은 아니다. 이 세부 정책과 접근 범위는 실제 개선용 로그 수집 전에 PM이 확정한다(D08).

## 9. 모의 발행 검증 계획

### 9.1 필수 검증 환경

**공식 API 규격을 참고한 자체 Mock API**를 사용한다. 실제 팝빌 인증·발행 검증은 7주 필수 완료 기준에서 제외한다.

자체 Mock에 필요한 최소 정보만 저장한다. 거래처명·금액은 예시이며 실제 팝빌 필수 항목 전체를 뜻하지 않는다. 내부 요청 필드와 공식 규격에서 참고·생략하는 항목은 구현 전에 정한다(D09).

### 9.2 검증 시나리오

- 정상 모의 발행
- 필수 정보 누락
- 처리 지연·응답 시간 초과
- 중복 요청
- 실패 사유 표시
- 화면 재진입 후 상태 확인

가상 응답으로 프론트엔드 안내와 상태 조회 흐름을 확인하고, 백엔드 상태 저장과 중복 생성 방지도 함께 검증한다.

### 9.3 화면 표시

저장 상태는 **`requested`(요청됨), `issued`(모의 완료), `failed`(실패)** 3개로 제한한다. `issued`를 실제 발행·국세청 전송 완료로 표시하지 않는다.

시간 초과 시 같은 요청의 상태를 조회하고, 재시도가 중복 모의 발행으로 이어지지 않도록 한다. 화면의 '처리 중·결과 확인 중' 안내와 DB 상태는 구분하며, 별도의 네 번째 상태를 추가하지 않는다. 정확한 전이·오류·재조회 규격은 D09에서 정한다.

## 12. 완료 기준과 최종 산출물

### 12.1 최종 목표

**7주 차까지 서비스 개발·배포와 전체 E2E 통합 QA, 버그 수정, 최종 데모 시연 리허설을 완료한다.**

### 12.2 필수 제품 검증

- 입력 → AI 후보 → 확인·수정 → 장부 확정
- 확인 전 장부 미반영 및 후보 거절 처리
- 모호한 정보의 추가 확인
- 중복 요청에 따른 중복 반영 방지
- 부분 입금의 거래처별 FIFO 차감
- FIFO 반영 후 거래별·거래처별 미수 잔액 일치
- 캘린더와 등록일별 확정 외상 거래 합계 일치
- 모의 발행의 정상·실패·지연 안내
- 화면 재진입 후 처리 상태 확인

추가 필수 검증은 3품목 초과 시 부분 저장 없이 400 응답, 다중 거래처 입력 거절, 단가 없는 입력의 `null` 처리·총액 확인, 단가가 있는 거래의 계산 불일치 400 응답, 초과 입금 차단, LLM 타임아웃·평가상 품질 저하의 Rule 전환, 마이크 권한 거부·STT 타임아웃의 텍스트 입력 전환이다. 인증·다른 사업자 데이터 접근 차단과 복구 절차의 세부 시나리오는 D02·D06·D07 결정 후 반영한다.

입금 취소·확정 거래 정정·사용자 삭제 UI, Admin UI 및 오류 TTS는 MVP에서 제외한다. CS 스크립트의 본인·소유권 확인·PM 승인·백엔드 담당자 실행·audit_log 기록·Soft Delete 집계 제외와 입금·모의 발행 연결 건 처리 차단을 검증한다. 수량 누락 보완, 선택 필드 비추정, 모든 품목 금액 제공 시 합계 대조와 산술 모순의 텍스트 모달 안내도 확인한다.

정확도 95% 미달만으로 배포를 중단하지 않으며, 음성 안정화 지연 시에는 텍스트 중심으로 전환한다. 기능 결함이 남았을 때의 데모·제한 베타·실사용 배포 범위는 PM이 결정한다(D10). 텍스트 중심 전환이 인증·데이터 정합성 검증을 생략한다는 의미는 아니다.

### 12.3 AI 실험 산출물

- 클라우드 LLM·Rule의 금액 Exact Match·필수 필드 F1 비교 결과
- 모델·프롬프트·평가 데이터 버전 및 실행 조건
- 주요 오류 유형과 적용 한계
- 피드백 반영 전후 비교 결과 1회 이상
- 최종 평가 결과와 해석

비용 절감이나 성능 향상이 확인되지 않아도 결과를 그대로 기록한다. **거래 전체 정확도 95%는 연구 목표이며 필수 합격선이 아니다.** 모델 탐색 중단 시 이유·기존 결과·적용 모델을 남기되, 사용자 피드백 기반 프롬프트 개선 전후 비교 최소 1회는 면제하지 않는다. 로컬 SLM·하이브리드 비교 결과는 수행한 경우에만 선택 산출물로 제출한다.

### 12.4 최종 산출물

- 배포된 서비스와 데모 시나리오
- API·데이터 구조 문서
- 평가 데이터·채점 기준·실험 결과
- 테스트 결과와 알려진 제한사항

### 14.2 PM 최종 확정안과 남은 구현 세부사항

팀 의견으로 확정한 범위는 14.1과 관련 본문에 반영했다. D02·D03·D06의 아래 정책은 최종 확정이며, 하단 표는 정책을 다시 결정하는 목록이 아니라 남은 구현·운영 계약을 구분한 것이다. 통합정리 문서의 다른 추천안은 PM 결정 전까지 확정 정책으로 취급하지 않는다.

팀 최종 답안에 따라 단가 null 검증·수량 보완, 오류 TTS 제외, CS 스크립트·Soft Delete·연결 거래 Lock, 선택 필드 오류 분리 보고, 시장·경쟁 표현 원칙은 확정했다. 남은 것은 위 표의 구현 계약과 검증 작업이다. 시장 통계 확인과 경쟁 서비스 조사는 PM 또는 기획 담당자가 1주차 종료 전까지 개발과 병렬로 진행한다. 직접 근거가 없는 210만은 계산용 가정에만 남기며 경쟁 기능은 공식 근거 확인 전 '미확인'으로 표시한다.

**최종 결정권은 PM에게 있다.** 결정값·일자를 기록한 뒤 관련 본문·API·DB·검증 기준을 함께 갱신한다. 후속 가격·한도·수익성·지불 의사 검토는 13장에서 관리한다.

공식 참고자료와 코드 활용 계획은 3.4·7.4, 초기 데이터 구축·평가·사용성 관찰 원칙은 8장에 반영했다. 시장 수치의 직접 근거 통계표, 유사 서비스 실제 사용 비교, 구현 코드 검증 및 위 표의 세부 선택은 아직 완료되지 않았다.
