### 0.1 회의 결정 상세 (2026-09-28 회의 안건 6 — 승현·수경)

**D03-4 표현 난이도 (6-4)**
- 4조건(① 어순 ② 정정·군더더기 없음 ③ 필수 5종 직접 등장 ④ 표준 단위·정수 수량)을 레코드에 **불린 4개**로 저장한다.
- 미검수는 `null`로 두어 `false`와 구분한다. 4개가 모두 `true`면 `명확한 표현`, 하나라도 `false`면 `복잡·생략 표현`, 하나라도 `null`이면 **라벨을 산출하지 않는다**.
- `difficulty_label`은 사람이 적지 않고 **build.py가 AND로 자동 산출**한다.
- 조건 ④의 "표준 단위"는 **열거 목록**으로 정의한다. 이 목록은 **난이도 판정에만** 쓰고 파싱·검증에는 쓰지 않는다 (단위 값은 D04-3대로 원문 유지). 단위 미언급·구어 축약의 판정 예시를 목록과 함께 둔다.
- **판정 해석 (PM 확정 2026-09-28, Golden 40건 검수 중):**
  - 조건 ① 어순에서 **금액과 결제 표현의 앞뒤 순서는 따지지 않는다** ("외상 육만 원" = "육만 원 외상"). 거래처가 앞, 품목·수량이 금액 앞이면 충족.
  - **합계형**(품목 여럿에 총액만 발화, 예: 012·015·021·029)도 4조건을 모두 채우면 `명확한 표현`. 품목 수·품목별 금액 유무는 난이도 조건이 아니다.
  - 조건 ② 군더더기: 말 조각마다 붙는 **'요'**("대박마트요", "한박스요", "이만원이요")는 군더더기다. 문장 끝 존댓말("달아주세요")은 아니다.
  - 단위가 수량 앞에 와도 단위로 본다 ("떡볶이재료 세트 하나" → 단위 `세트`). 상품을 구분하는 수식어는 품목명에 포함한다 ("세제 대용량").
- 목표 건수는 **난이도 × 기대 결과 4칸 교차표**로 지정한다. 최종 평가용 40건은 [출제 설계표 §1.2](golden_60_출제설계표.md) (18/6/10/6). 개발용 60건의 4칸 목표는 추가로 정한다.

**D03-6 채점 정규화 (6-6)**
- 거래처·품목명: 공백 제거 후 완전 일치. 단 **공백 차이 때문에만 통과한 건수를 필드 단위·거래 단위로 따로 집계·보고**한다.
- 수량: `Decimal` 수치 비교 (`5` = `5.0`). `null`과 `0`은 다르다.
- `unit`: 정규화 없이 완전 일치.
- `credit`: `true` / `false` / `null` 세 값으로 비교.

**D03-8 품목 대응·F1 (6-7)**
- micro 평균, 품목 순서 무관 매칭.
- 매칭 키는 **`name` 단독**, 같은 이름이 여럿이면 **multiset 1:1 매칭**.
- 필수 필드 F1은 **기대 결과 = `정상 구조화 가능`** 건만 대상으로 한다.
- 잘못된 필드값은 **FP 1 + FN 1**로 집계한다. 평가 대상 정답값과 예측값이 모두 없어 F1 분모가 0일 때만 `N/A`로 표시한다.
- 선택 필드의 null·누락 처리와 매칭 우선순위는 **채점 명세에 고정**한다.

### 0.2 채점 세부 규칙 — 확정 (2026-09-29, 김수경 안 + PM 보완)

| # | 질문 | 제안 | 결정 |
|---|---|---|---|
| ① | 추가 확인 4종(D03-5)과 API 오류 코드(DL-03)의 관계 | 4종은 **채점 그룹**으로 유지하고, 레코드에 **기대 오류 코드** 필드를 따로 둔다 | **확정.** `confirm_type`(채점 분류)과 **`expected_error_code`**(API 기대 코드)를 분리. `build.py`가 산출하고, 입력 범위 위반은 보완 필드 `["counterparty"]`→`MULTIPLE_COUNTERPARTIES_DETECTED`, `["items"]`→`EXCEED_MAX_ITEMS`로 구분 (035·036 수정). **추가 확인 적합성 = 400 + 기대 오류 코드 일치 + 보완 필드 + 값을 지어내지 않음.** `message` 문구는 채점하지 않는다 |
| ② | `name`이 틀려 매칭되지 않은 품목의 채점 | (PM 초안: 매칭 안 된 품목끼리 순서로 짝짓기 — **기각**) | **확정 (김수경 안).** 품목은 **공백 제거 후 `name` 일치만** 대응. 순서로 짝짓지 않는다 (다른 상품의 수량을 맞았다고 인정하는 오류 방지). 이름이 틀리면 정답 품목의 `name`·`qty`는 FN, 예측 품목의 `name`·`qty`는 FP — 의도된 감점. **필수 필드 F1의 품목 필드는 `name`·`qty`만**이고 선택 필드는 ④로 집계. 동명 품목은 **수량 일치가 가장 많은 1:1 대응** (검증 사례를 개발용 신규 20건에 1~2건 포함) |
| ③ | 예측에 키가 없을 때 | 키 누락 = `null`로 간주 | **확정.** 필수 필드: 같은 값 TP / 키 없음·`null` FN / 다른 값 FP 1 + FN 1. `0`·`false`·`""`는 `null`이 아니다 (`credit: false`는 정상 값). 자료형 오류는 `null`로 바꾸지 말고 **형식 오류로 따로 기록**. 이것은 채점 규칙일 뿐, **API가 필수 키를 생략해도 된다는 뜻이 아니다** |
| ④ | 선택 필드(D03-7) 집계 | 품목별·필드별 건수 | **확정.** 정답 `null`·예측 없음 → 오류 없음 / 정답 `null`·예측 값 → **선택 필드 FP** / 같은 값 → 오류 없음 / 다른 값 → FP / 정답 값·예측 없음 → **FP 아님, "선택 필드 누락"으로 따로 집계**. 누락은 거래 전체 정확도에 반영하지 않는다 (기획서 §8.3). 단일 품목 총액 → 품목 금액(규칙 7)은 명시된 품목 금액과 충돌하지 않을 때만 (G2) |
| ⑤ | 오류가 여러 개 겹칠 때 | — | **확정 (PM).** API는 코드 하나만 반환. 우선순위 `INPUT_TOO_LONG` → `MULTIPLE_COUNTERPARTIES_DETECTED` → `EXCEED_MAX_ITEMS` → `MISSING_REQUIRED_FIELD` → `AMOUNT_OUT_OF_RANGE` → `AMOUNT_MISMATCH`. `problem_fields`는 반환한 코드의 필드만. Golden도 건당 `confirm_type` 하나 (DL-03) |

**후속 작업:** 채점 명세 문서 `data/golden/SCORING.md` (담당 AI·김수경) · 기존 40건에 4조건 불린 부여 (PM 검수와 함께) · 표준 단위 열거 목록 · 개발용 4칸 목표.

## D04-1 · 거래처 명칭을 발화에서 어디까지 잘라낼 것인가 ★

### 무엇이 문제인가

기획서 5.1은 *"신규 거래처는 입력·STT 명칭을 사용하며 별칭·병합 기능은 제외한다"*고 확정했다. 그런데 "입력 명칭"이 어디부터 어디까지인지는 정하지 않았다. 아래 네 건이 실제로 갈린다.

| 발화 | 후보 A | 후보 B |
|---|---|---|
| 철수**씨한테** 양파 십킬로 | 철수씨 | 철수 |
| 박씨 **가게로** 무 다섯 개 | 박씨 가게 | 박씨 |
| 영수네 **가게에** 사과 한 박스 | 영수네 가게 | 영수네 |
| 철수**씨 가게** 마늘 한접 | 철수씨 가게 | 철수 |

### 선택지

| 안 | 규칙 | 결과 |
|---|---|---|
| **A (권장)** | 조사(한테/에게/에/로/으로/요)와 위치어(쪽/편)만 제거. 나머지 문자열은 그대로 | 철수씨 / 박씨 가게 / 영수네 가게 / 철수씨 가게 |
| B | 호칭 접미사(씨/님/사장님)와 일반명사(가게/집)도 제거 | 철수 / 박씨 / 영수네 / 철수 |

### 권장: A

- 5.1의 "입력·STT 명칭을 사용"에 가장 가깝다. B는 사실상 정규화이고, 기획서가 제외한 별칭 처리에 한 발 들어간다.
- 채점이 기계적으로 가능하다. B는 "어디까지가 호칭인가"를 매번 판단해야 하고, 그 판단이 곧 AI 추정이다.
- 8.3의 "근거 없이 생성된 값" 원칙과 방향이 같다.

### A를 택했을 때 남는 문제 — 반드시 함께 읽을 것

거래처가 문자열로 갈라진다.

| 실제로는 같을 가능성이 높은 묶음 | 저장되는 거래처 |
|---|---|
| `g-dev-004` / `g-dev-016` / `g-dev-026` | 철수씨 · 철수네 · 철수씨 가게 |
| `g-dev-007` `025` `039` / `g-dev-015` | 박씨네 · 박씨 가게 |
| `g-dev-002` / `g-dev-012` `022` | 영수네 가게 · 영수네 |
| `g-dev-005` `014` `037` / `g-dev-024` | 한식당 · 한식집 |

**FIFO에 직접 영향이 간다.** 철수네 앞으로 외상 3건이 쌓였는데 입금이 "철수씨"로 들어오면 차감할 외상이 없다. 기획서 5.2의 "거래처별 확정 외상을 FIFO 차감"이 전제하는 거래처 동일성이 깨진다.

이것은 데이터 오류가 아니라 **5.1이 별칭·병합을 제외한 데서 오는 제품 한계**다. 두 가지를 함께 결정해야 한다.

1. MVP 화면에서 기존 거래처를 **선택**할 수 있게 할 것인가, 매번 새로 생성할 것인가
2. 사용 안내에 "거래처명이 다르면 다른 거래처로 관리됩니다"를 명시할 것인가

→ D04-2로 이어짐

## D04-2 · 동명·유사 거래처 식별

| 안 | 규칙 | 장단점 |
|---|---|---|
| **A (권장)** | 문자열 완전 일치만 같은 거래처. 후보 확인 화면에 **기존 거래처 목록을 제시**하고 사용자가 고르면 그 거래처로 연결 | 자동 병합 없이도 FIFO가 깨지지 않음. 프론트 작업 1건 추가 |
| B | 완전 일치만 같은 거래처. 선택 기능 없음 | 5.1에 가장 충실하나 FIFO 분산이 그대로 남음 |
| C | 공백·호칭 제거 후 비교해 자동 병합 | 5.1이 제외한 병합 기능에 해당 → 범위 위반 |

**권장 A의 근거.** 사용자가 고르는 것은 별칭 생성이 아니라 기존 레코드 참조다. 5.1이 제외한 "별칭·병합 기능"에 해당하지 않으면서 FIFO 분산을 막을 수 있다. 다만 화면 작업이 늘어나므로 **일정 여유가 없으면 B + 사용 안내 명시**로 간다.

## D04-3 · 수량 단위 처리

| 안 | 규칙 |
|---|---|
| **A (권장)** | 발화에 등장한 단위 문자열을 그대로 저장. 단위 간 환산 없음. 단위가 없으면 `null` |
| B | 표준 단위 코드로 정규화 (킬로/kg/㎏ → `kg`) |

**권장 A.** 8.3이 단위를 선택 필드로 두고 "원문과 다르거나 근거 없이 생성된 선택 필드는 오류"로 집계하므로, 정규화는 정답 판정을 흐린다. 환산은 MVP 범위 밖이다.

**확정해야 할 부수 규칙.** "하나", "한", "두"는 수량이지 단위가 아니다. `g-dev-018`("세제 하나 칠천원")과 `g-dev-034`("세제 대용량 하나")는 v1.0에서 `unit: "개"`로 되어 있었고, v2.0에서 `null`로 고쳤다. 반면 `g-dev-028`("떡볶이재료 세트 하나")은 "세트"가 발화에 있으므로 유지한다.

## D04-4 · 소수 수량과 반올림

| 항목 | 권장안 |
|---|---|
| 소수 수량 | 허용. `qty`는 number(소수점 2자리까지) |
| 금액 계산 | 수량 × 단가는 **원 단위 반올림**(소수점 첫째 자리에서) |
| 총액 | 품목 금액의 단순 합. 재반올림 없음 |
| 비교 허용 오차 | 0원. 1원이라도 다르면 산술 모순으로 400 |

`g-dev-024`("이점오킬로 킬로에 구천오백원")가 2.5 × 9,500 = 23,750으로 정수가 나와 지금은 문제가 없다. 그러나 2.5 × 9,900 = 24,750, 1.3 × 1,500 = 1,950처럼 소수가 나오는 조합은 곧 등장한다. **반올림 기준 없이 400을 띄우면 정상 거래가 거절된다.**

## D04-6 · 현금·외상이 언급되지 않았을 때 ★

### 무엇이 문제인가

기획서 8.1의 `expected_json` 예시는 `"credit": true` 하나뿐이다. **미기재를 표현할 값이 없다.** 그런데 8.3은 외상 여부를 필수 필드 5종에 넣었고, 8.1은 *"'사과랑 배 합쳐서 10만 원'은 거래처·수량·**외상 여부**가 부족한 추가 확인 사례"*라고 했다.

해당 건: `g-dev-004` `g-dev-009` `g-dev-034` (3건)

### 선택지

| 안 | 스키마 | 미기재 시 동작 |
|---|---|---|
| **A (권장)** | `credit: true \| false \| null` | `null` → 필수값 누락 → HTTP 400 보완 요청 |
| B | `credit: boolean` + `payment_method: "현금"\|"카드"\|"외상"\|null` | 결제수단을 따로 기록. 필드가 하나 늘고 채점 규칙도 늘어남 |
| C | 미언급은 외상으로 간주 | 현장 관행에는 맞지만 8.3의 필수 필드 정의와 충돌하고, 틀리면 없던 외상이 생김 |

**권장 A.** 8.1의 예시가 외상 여부 누락을 추가 확인 사례로 명시했으므로, `null` + 보완 요청이 기획서와 일치한다. C는 잘못 추정하면 장부에 없던 외상이 남아 FIFO까지 오염된다.

**부수 결정: 카드 결제.** 현재 `g-dev-006` `g-dev-018`은 카드를 `credit: false`(현금성)로 처리했다. 카드는 입금이 며칠 뒤이지만 사업자가 외상으로 관리하지는 않으므로 타당하다. **MVP에서는 카드 = 즉시 결제로 확정하고 화면 안내에 명시**할 것을 권한다.

## D04-7 · 총액을 말하지 않은 거래를 어떻게 볼 것인가

### 무엇이 문제인가

거래 총액은 8.3의 필수 필드 5종 중 하나다. 그런데 현재 40건 중 **14건은 발화에 총액이 없고 계산으로 도출**했다.

```
g-dev-017  꽃게집에 꽃게 오마리 마리당 만오천원 외상   → 5 × 15,000 = 75,000
g-dev-013  대박마트 콜라 한 박스 만이천원에 과자 다섯 개 오천원 외상 → 12,000 + 5,000 = 17,000
```

이것을 "필수 필드 누락"으로 보면 14건이 전부 추가 확인 필요가 된다.

### 권장안

**단가 × 수량 또는 전 품목 금액 합계로 총액이 유일하게 결정되면 `정상 구조화 가능`으로 본다.**

근거: 5.1이 "모든 품목의 금액이 제공된 경우 품목 금액 합계와 거래 총액을 반드시 대조한다"고 하여 합계 도출을 전제하고 있다. 또 8.1은 "단가 생략이 있어도 필수 정보가 모두 있으면 정상 구조화 가능"이라고 하여 도출 가능성을 필수 정보 충족으로 본다.

**함께 정할 것.** 도출 총액인지 발화 명시 총액인지 구분하는 메타 필드(`notes.total_source`)를 둔다. 금액 Exact Match 분모 처리(D03-9)와 연결된다.

## D03-1 · 총량과 두 세트 분할 ★

기획서 8.1: *"Golden Set은 개선 비교용(개발용)·최종 평가용 합계 50–100건으로 구축한다. 총량을 늘리거나 최종 평가용만 50–100건을 확보하는 것이 아니다."*

| 안 | 개발용 | 최종 평가용 | 개발용 정상 사례 | 1건의 가중치 |
|---|---:|---:|---:|---:|
| **A (권장)** | 60 | 40 | 42 | 2.4%p |
| B | 50 | 50 | 35 | 2.9%p |
| C | 40 (현재 그대로) | 60 | 28 | 3.6%p |

**권장 A.** 기획서 6.5는 80% 운영 전환 판단에 개발용 Golden만 쓰도록 했다. 이 판정의 분모는 `정상 구조화 가능` 사례 수이므로 개발용이 커야 경계에서 덜 흔들린다. C안은 1건 차이가 3.6%p여서, 80% 경계에서 두 건만 틀려도 Rule 전환이 결정된다.

## D03-2 · 최종 평가용 6:4 정수 배분

기획서 D03 확정: 최종 평가용 **내부에만** 명확한 표현 60% / 복잡·생략 표현 40%.

40건 기준 → **명확한 표현 24건 / 복잡·생략 표현 16건** (정수로 떨어짐)

개발용에는 이 비율을 적용하지 않는다. 다만 현재 개발용 40건이 명확한 표현 11건(27.5%)으로 치우쳐 있어, 신규 20건으로 41.7%까지 올릴 것을 권한다. (사유는 출제 설계표 1.1)

## D03-3 · 기대 결과별 사례 수

표현 난이도와 **독립 라벨**이다(기획서 8.1). 교차표로 관리한다.

| 세트 | 정상 구조화 가능 | 추가 확인 필요 |
|---|---:|---:|
| 개발용 60 | 42 (70%) | 18 (30%) |
| 최종 평가용 40 | 28 (70%) | 12 (30%) |

**30%를 권하는 이유.** 8.3의 "추가 확인 적합성"은 독립 트랙 지표다. 현재 v1.0의 5건(12.5%)이면 1건이 20%p씩 움직여 지표로 쓸 수 없다. v2.0에서 12건(30%)이 되어 1건이 8.3%p가 되었고, 60건 기준 18건이면 5.6%p가 된다.

## D03-4 · 표현 난이도 판정 체크리스트 ★

기획서는 라벨 이름만 정하고 판정 기준을 남겼다. 아래 4조건을 **전부 충족**하면 `명확한 표현`, 하나라도 위배하면 `복잡·생략 표현`으로 할 것을 권한다.

| # | 조건 |
|---|---|
| 1 | 어순이 [거래처 → 품목 → 수량 → 금액 → 결제] 흐름을 벗어나지 않는다 |
| 2 | 정정·번복·잡담·군더더기 발화가 없다 |
| 3 | 필수 필드 5종이 모두 발화에 **직접** 등장한다 (계산 도출이 필요 없다) |
| 4 | 표준 단위이고 수량이 정수이며 구어 축약이 심하지 않다 |

### 이 기준을 적용한 결과

v1.0의 easy/medium/hard 3단계를 2단계로 접으면 이렇게 된다.

| v1.0 | 건수 | → 명확한 표현 | → 복잡·생략 표현 |
|---|---:|---:|---:|
| easy | 14 | 9 | 5 |
| medium | 17 | 1 | 16 |
| hard | 9 | 1 | 8 |

easy 중 5건이 복잡·생략으로 내려간 것은 조건 3(수량·외상 여부 누락) 때문이고, medium·hard 중 2건(`037` `039`)이 명확으로 올라온 것은 산술 모순 사례라 표현 자체는 또렷하기 때문이다. **이 2건이 "명확한 표현 × 추가 확인 필요" 조합의 예시**이고, 최종 평가용 6:4와 기대 결과 30%를 동시에 맞추려면 이 조합이 반드시 필요하다.

## D03-5 · confirm_type 하위 라벨 신설 ★

### 무엇이 문제인가

`추가 확인 필요` 한 라벨 안에 **채점 방식이 다른 사례가 섞여 있다.**

```
g-dev-001  수량 누락        → 사용자에게 "수량을 알려주세요" (필드 보완 요청)
g-dev-036  5품목 초과       → "최대 3개까지만 입력 가능합니다" (재입력 안내)
```

8.3의 추가 확인 적합성 정의는 *"값을 지어내지 않고 실제 누락·모순 필드의 **보완을 요청**한 건수"*다. 범위 위반은 보완 요청이 아니라 재입력 안내이므로, 같은 식으로 채점하면 분자 정의가 흔들린다.

### 권장: 하위 라벨 4종 신설

| `confirm_type` | 정의 | 기대 동작 | 현재 40건 |
|---|---|---|---:|
| `필수값 누락` | 필수 필드 5종 중 일부가 발화에 없음 | 400 + 누락 필드 명시 + 수정 폼 | 8 |
| `산술 모순` | 수량×단가 ≠ 금액, 또는 품목 합 ≠ 총액 | 400 + 모순 지점 명시 | 2 |
| `입력 범위 위반` | 3품목 초과, 다중 거래처 | 400 + 재입력 안내 (후보 생성 보류) | 2 |
| `금액 범위 위반` | 금액·수량이 허용 범위 밖 | 400 + 범위 안내 | 0 → F/R 유형으로 보충 |

채점은 유형별로 나눈 뒤 합산 보고한다. 기획서 8.3의 "정답 건수와 분모를 함께 보고" 원칙과 맞는다.

## D03-6 · 필수 필드 정규화 기준

| 필드 | 비교 방법 |
|---|---|
| `counterparty` | 앞뒤 공백 제거 후 **완전 일치**. 내부 공백은 유지(`박씨 가게` ≠ `박씨가게`는 오답 처리하지 않도록 내부 공백도 제거 후 비교 권장) |
| `items[].name` | 앞뒤·내부 공백 제거 후 완전 일치 |
| `items[].qty` | 수치 비교. `5` = `5.0` |
| `total_amount` | 정수 완전 일치 |
| `credit` | `true` / `false` / `null` 완전 일치 |

**권장: 내부 공백도 제거 후 비교.** STT는 띄어쓰기를 불규칙하게 넣는다. `박씨 가게`와 `박씨가게`를 다르게 채점하면 측정하려는 것(정보 추출)이 아니라 띄어쓰기를 측정하게 된다.

**함께 정할 것.** `items[].name`의 수식어 처리. `g-dev-034`("세제 대용량 하나")의 품목명을 `세제`로 할지 `세제 대용량`으로 할지가 미정이다. 현재 v2.0은 `세제`로 두었으나 D04-1에서 거래처에 "원문 유지"를 택하면 품목명도 같은 원칙을 적용하는 것이 일관적이다.

## D03-7 · 선택 필드 오류 집계 규칙

8.3: *"원문과 다르거나 근거 없이 생성된 선택 필드는 선택 필드 오류(False Positive) 건수로 별도 보고한다. 이 오류를 필수 필드 기반 거래 전체 정확도에 직접 합산하지 않는다."*

| 항목 | 권장안 |
|---|---|
| 집계 단위 | **품목별 × 필드별 건수**. 한 거래에서 2품목의 `unit`이 모두 날조되면 2건 |
| 대상 필드 | `unit`, `unit_price`, `items[].amount` |
| FP 판정 | 정답이 `null`인데 값이 생성됨 / 정답과 다른 값이 생성됨 |
| 생략 | 정답이 `null`이고 예측도 `null`·키 없음 → 정상 (오류 아님) |
| 보고 | 총 FP 건수 + 필드별 내역. 거래 전체 정확도와 분리 |

**단일 품목 예외를 명시해야 한다.** `g-dev-002`("사과 한 박스 현금 이만 원")처럼 품목이 하나이고 총액만 제시된 경우, `items[0].amount = 20000`은 근거 있는 파생값이므로 FP가 아니다. 정답셋에도 채워 두었다. 2품목 이상일 때 총액을 나눠 넣는 것만 FP다.

## D03-8 · 품목 대응·F1 평균·분모 0 처리

| 항목 | 권장안 |
|---|---|
| 품목 대응 | **순서 무관**. `name` 일치를 우선으로 정답·예측 품목을 최적 매칭. 동명 품목이 둘이면 등장 순서로 |
| 누락 품목 | 정답에 있고 예측에 없음 → 해당 품목의 모든 필드를 FN |
| 추가 품목 | 예측에만 있음 → 모든 필드를 FP |
| F1 평균 | **micro 평균**(전체 TP/FP/FN 합산 후 계산). 건별 macro는 품목 수에 따라 가중이 왜곡됨 |
| 분모 0 | 평가 대상 필드가 0건이면 해당 지표는 `N/A`로 보고. **0%로 기록하지 않는다** |
| 생성 실패 | JSON 변환 실패는 전 필드 FN으로 집계 (기획서 7장) |

## D03-9 · 금액 Exact Match의 분모 처리

8.3 정의: *"총액 정답이 있는 대상 중 후보 총액이 정확히 일치한 건수 / 총액 정답이 있는 평가 건수"*

현재 40건 중 **14건은 총액이 발화에 없고 계산으로 도출**된 건이다(D04-7).

| 안 | 처리 |
|---|---|
| **A (권장)** | 도출 총액도 분모에 포함. 단 `total_source`로 구분해 **발화 명시 / 계산 도출을 나눠서도 보고** |
| B | 도출 총액은 분모에서 제외 | |

**권장 A.** 8.3이 제외 조건을 두지 않았고, 실제 서비스에서도 도출 총액이 장부에 들어간다. 다만 두 유형은 실패 원인이 다르다(전사 오류 vs 계산 오류). 나눠 보고하면 오류 분석에 쓸 수 있다.

현재 분포: 발화 명시 24건 / 계산 도출 14건 / 해당 없음 2건

## D03-10 · group_id 분할 기준

8.1: *"문장만 조금 바꾼 동일 거래 유형이 서로 다른 세트에 섞이지 않도록 분리 기준을 정한다."*

| 규칙 | 내용 |
|---|---|
| 정의 | `group_id` = 하나의 원본 문장과 그것을 변형해 만든 문장들의 묶음 |
| R1 | 같은 `group_id`는 반드시 같은 세트에 둔다 |
| R2 | 구조 템플릿(단가형·합계형 등)은 두 세트에 모두 등장해도 된다 |
| R3 | **거래처명은 세트 간에 재사용하지 않는다** ← 실질적인 누출 차단선 |
| R4 | Golden 문장은 프롬프트 예시·Seed로 재사용하지 않는다 |

현재 40건은 15개 그룹(G01-G15)으로 묶었고 전부 개발용이므로 세트 간 누출은 없다. 최종 평가용 40건은 새 `group_id`와 **새 거래처명 풀**을 쓴다.

> **확인 필요.** 지금 작성 중인 `golden_dev.jsonl` 원본에 `group_id`가 들어 있는지 확인이 필요하다. 없다면 지금 붙이는 편이 100건을 다 만든 뒤보다 훨씬 쉽다.
