# Golden Set 남은 60건 출제 설계표

> 기준 문서: 에코빌 기획서 5.1 / 7.1 / 8.1 / 8.3 / 14.1 / 14.2
> 현재 상태: 개발용 Golden 기존 40건 PM 검수 완료, 신규 20건 PM 검수 완료 2026-09-29(`golden/golden_dev.jsonl`, v2.5)
> 이 문서의 건수 배분은 **D03 결정안(개발용 60 / 최종 평가용 40)**을 전제로 한다. D03이 다르게 결정되면 전체 표를 다시 계산해야 한다.

## 0. 먼저 확인할 전제

기획서 8.1은 Golden Set 총량을 **개선 비교용(개발용)과 최종 평가용의 합계 50–100건**으로 정했다. "각각 50–100건"이 아니다.

따라서 지금 만들고 있는 100건은 **상한선**이며, 그 안에서 두 세트로 나눠야 한다.

| 세트 | 건수 | 용도 | 현재 |
|---|---:|---|---|
| 개발용 Golden | 60 | 모델 비교, 개선 전후 반복 평가, **80% 운영 전환 판단** | 60건 PM 검수 완료 (신규 20건 2026-09-29) |
| 최종 평가용 Golden | 40 | 최종 성능 보고 전용. 모델 선택·전환·복귀 판단에 사용 금지 | **40건 신규** |
| 합계 | 100 | | **60건 출제 대상** |

**개발용을 더 크게 잡는 이유.** 기획서 6.5는 80% 운영 전환 판단에 개발용 Golden만 쓰도록 했다. 이 판정의 분모는 `정상 구조화 가능` 사례 수이므로, 개발용 쪽이 작으면 한두 건 차이로 Rule 전환이 결정된다. 개발용 정상 사례를 42건까지 늘리면 1건이 2.4%p가 되어 80% 경계에서 흔들림이 줄어든다.

## 1. 목표 배분

### 1.1 개발용 Golden 60건

표현 난이도 6:4 제약은 기획서 D03에 따라 **최종 평가용 내부에만** 적용된다. 개발용에는 비율 의무가 없지만, 아래 이유로 명확한 표현을 40% 이상 확보할 것을 권한다.

> 기존 40건의 4조건 산출 결과는 명확한 표현 15건(37.5%)이다. 신규 20건에서도 명확한 표현 14건을 확보해 난이도 편중을 줄인다.

| 구분 | 기존 40건 | 신규 20건 | 개발용 합계 60건 |
|---|---:|---:|---:|
| 명확한 표현 | 15 | **14** | 29 (48.3%) |
| 복잡·생략 표현 | 25 | **6** | 31 (51.7%) |
| 정상 구조화 가능 | 28 | **14** | 42 (70.0%) |
| 추가 확인 필요 | 12 | **6** | 18 (30.0%) |

### 1.2 최종 평가용 Golden 40건

D03 확정 사항인 6:4를 정수로 배분한다.

| 교차 | 건수 |
|---|---:|
| 명확한 표현 × 정상 구조화 가능 | 18 |
| 명확한 표현 × 추가 확인 필요 | 6 |
| 복잡·생략 표현 × 정상 구조화 가능 | 10 |
| 복잡·생략 표현 × 추가 확인 필요 | 6 |
| **합계** | **40** |

표현 난이도 명확 24 / 복잡·생략 16 = 6:4 ✅
기대 결과 정상 28 / 추가 확인 12 = 70:30 (개발용과 동일 비율로 맞춤)

**주의.** 기획서 8.1은 "6:4를 정상 처리·추가 확인 사례 비율로 해석하지 않는다"고 명시했다. 위 표처럼 두 라벨을 교차로 관리해야 한다.

### A 유형을 넣는 이유 — 숫자 표기 짝 비교

현재 40건은 **숫자가 전부 한글 표기**다("삼만 원", "만오천원", "이점오킬로"). 그런데 STT 결과는 아라비아 숫자로 나오는 경우가 많다. 기획서 8.1은 템플릿 변형 요소로 **숫자 표기**를 첫 번째로 지목했고, 6.2의 STT 선정 기준에도 "숫자·단위·품목 인식"이 있다.

A 유형은 **기존 문장의 숫자 표기만 바꾼 변형**이다. 같은 `group_id`를 유지하므로 세트 간 누출 문제가 없고(둘 다 개발용), 표기 차이가 정확도에 주는 영향을 직접 측정할 수 있다.

```
원본  g-dev-003  대박마트에 계란 두판 사만오천원 달아놔
변형  g-dev-041  대박마트에 계란 2판 45000원 달아놔        ← group_id G01 동일
```

실제 변형 대상 8건: `003` `005` `010` `012` `015` `025` `029` `032`.
— 명확 6건·복잡 2건이며, 모두 `정상 구조화 가능`이다. 원본과 같은 `group_id`를 유지한다.

**2026-09-29 재작성안 (PM 검수 완료 2026-09-29):** A의 단순 단일품목 3건을 2품목 합계형 짝으로 교체해 품목별 금액 추정 오류를 확인한다. B에 실제 수량·결제 정정을 넣고, F의 0원 사례에서 난이도만 높이던 군더더기는 제거했다. B/F의 난이도 배분만 조정하여 신규 전체 명확 14 / 복잡 6은 유지한다. C의 동명 품목은 서로 다른 거래에 같은 이름을 쓰는 것이 아니라 **한 거래 안에서 같은 name의 두 줄을 수량 기준으로 1:1 대응**하는 사례다. 검수 포인트는 [추가20건_검토안](golden/추가20건_검토안.md)에 정리한다.

## 4. 숫자 표기 목표 비율

신규 60건 전체 기준이다.

| 표기 | 예시 | 건수 | 비율 |
|---|---|---:|---:|
| 한글 수 표기 | 삼만 원, 만오천원, 이점오킬로 | 18 | 30% |
| 아라비아 숫자 | 30000원, 30,000원, 2.5kg | 26 | 43% |
| 혼합 | 3만원, 2만5천원, 1.5kg, 2박스 | 16 | 27% |

세트별 배분: 개발용 신규 20건(한글 2 / 아라비아 12 / 혼합 6) · 최종 평가용 40건(한글 16 / 아라비아 14 / 혼합 10)

**남는 한계를 그대로 적어 둔다.** 기존 40건이 전부 한글 표기라, 위 계획대로 해도 개발용 60건은 한글이 42건(70%)으로 남는다. 완전히 해소하려면 기존 건의 일부를 표기 변형으로 재작성해야 하는데, 이는 A 유형 8건으로 부분적으로만 보완된다. 최종 평가용은 처음부터 목표 비율로 맞출 수 있으므로, **숫자 표기 영향은 최종 평가용 결과로 해석**하는 편이 안전하다.

### STT 출력 특성 반영

STT는 띄어쓰기와 쉼표를 자주 생략한다. 아라비아·혼합 표기 건 중 절반 이상은 아래처럼 쓴다.

```
30000원   45000원   2.5kg   2박스   1.5킬로
```

쉼표가 들어간 표기(`30,000원`)는 4건 이하로 제한한다. 실제 STT 출력에서 드물다.

## 5. 세트 분리 규칙 (누출 방지)

기획서 8.1: *"문장만 조금 바꾼 동일 거래 유형이 서로 다른 세트에 섞이지 않도록 분리 기준을 정한다. 분할은 원본 사례·템플릿과 파생 문장 그룹 단위로 수행한다."*

| 규칙 | 내용 |
|---|---|
| R1 | 같은 `group_id`는 반드시 같은 세트에 둔다 |
| R2 | 구조 템플릿(단가형·합계형 등)은 두 세트에 모두 등장해도 된다 |
| R3 | **거래처명은 세트 간에 재사용하지 않는다** — 이것이 실질적인 누출 차단선 |
| R4 | 품목명 + 금액 조합이 두 세트에 동일하게 나타나지 않게 한다 |
| R5 | Golden 문장은 프롬프트 예시·Seed로 재사용하지 않는다 (기획서 8.1) |

### 개발용이 이미 사용한 거래처명 23개 — 최종 평가용에서 사용 금지

### 최종 평가용 보관·평가 (2026-09-29, 기획서 §10)

- 최종 평가용 40건은 **PM이 레포 밖에서** 작성·보관한다. AI 초안은 **개발에 쓰지 않는 별도 세션**(claude.ai 시크릿 채팅 등)에서만 받고, PM이 전수 검수한다. 레포 개발 세션에는 문장을 넣지 않는다. 11/2 최종 평가 전에는 레포·노션·팀 채팅에 올리지 않는다 (레포 `.gitignore`가 `golden_test*` 반입을 막는다).
- 최종 평가(11/1~2)는 AI 담당의 채점 스크립트를 **PM이 직접** 실행하고, AI 담당은 점수만 받는다.

## 6. D04 결정 대기 예비 문항 6건 (100건에 포함하지 않음)

아래 유형은 기대 결과 라벨이 **D04 결정 없이는 정해지지 않는다.** 문장은 미리 써 두되, D04 확정 후 라벨을 붙여 편입 여부를 판단한다.

| 유형 | 건수 | 예시 | 무엇이 미정인가 |
|---|---:|---|---|
| 입금·수금 발화 | 2 | "김씨네 오만원 받았어" | 거래 입력 API에 들어왔을 때 거절인지, 입금 화면 안내인지 |
| 반품·취소 발화 | 2 | "어제 대박마트 콜라 한 박스 반품됐어" | 정정 UI가 MVP 제외이므로 처리 경로 자체가 없음 |
| 동명·유사 거래처 | 2 | "철수네 배추…" / "철수씨 배추…" | D04 거래처 생성·동명 식별 규칙에 따라 같은 거래처인지 갈림 |

**입금 발화를 특히 먼저 정해야 하는 이유.** 이 발화가 거래로 구조화되면 5만 원 외상이 새로 생긴다. 실제로는 외상이 5만 원 줄어야 하는 상황이므로, **장부가 10만 원 어긋난다.** FIFO 잔액 검증(12.2)을 통과해도 잡히지 않는 유형이다.

## 8. 출제 시 지킬 체크리스트

작성자용. 한 건을 쓸 때마다 확인한다.

- [ ] **매출 거래**다 (사 온 거래·매입 문장 금지, 결정안 G1)
- [ ] 발화에 없는 값을 `expected_json`에 넣지 않았다 (단위·단가·품목별 금액 포함)
- [ ] 수량이 없으면 1로 채우지 않고 `null` + `추가 확인 필요`로 두었다
- [ ] 단가가 있으면 수량 × 단가 = 품목 금액이 맞다
- [ ] 모든 품목 금액이 있으면 합계 = 총액이 맞다
- [ ] 일부 품목만 금액이 있으면 부분 합계를 총액과 비교하지 않았다
- [ ] 거래처명이 다른 세트에서 쓰이지 않았다 (개발용 신규는 `DEV_COUNTERPARTY_POOL`만)
- [ ] 산술 모순·범위 위반·품목 경로는 결정안 §0.4 G2~G6을 따랐다
- [ ] `group_id`가 한 세트 안에만 있다
- [ ] 표현 난이도와 기대 결과를 각각 독립적으로 판정했다
- [ ] `confirm_type`을 붙였다 (추가 확인 필요인 경우)
- [ ] `review_status`는 PM 검수 전까지 `미검수`다

## 9. STT 비교용 녹음 셋

결정 로그 DL-16(Whisper → CLOVA Speech / 리턴제로 1회 비교)에 쓸 음성 입력이다. 기획서 §6.1은 STT 비교에 **동일한 음성 입력**을 쓰도록 했는데, Golden은 텍스트뿐이라 별도로 만든다.

| 항목 | 기준 |
|---|---|
| 문장 출처 | **Dev Golden 검수 완료 건만.** 최종 평가용 문장은 녹음하지 않는다 (누출 방지) |
| 건수 | 20~30건 |
| 문장 구성 | 한글 숫자·아라비아 숫자 발화 혼합, 1~3품목, 거래처 고유명사가 있는 문장 우선. `추가 확인 필요` 건 일부 포함 |
| 녹음자 | 팀원 2~3명 (목소리·말투 다양성) |
| 기기·경로 | **실제 카카오톡 인앱 웹에서 녹음** (Android·iOS 각각). 1주차 인앱 녹음 검증과 같은 경로 |
| 환경 | 조용한 곳 위주 + 소음 환경 5건 내외 (시장·차량 등) |
| 정답 | 녹음 파일마다 해당 Golden `id`를 연결. STT 정답 텍스트는 Golden `utterance_text` |
| 보관 | **오디오는 레포에 커밋하지 않는다** (`.gitignore`). 팀 드라이브에 두고, 레포에는 `id`·파일명·녹음자·기기·환경을 적은 목록만 둔다. 팀원 녹음은 사용자 데이터가 아니지만 녹음자 동의를 받는다 |
| 평가 | 같은 파일을 각 STT에 넣고 **STT → 파서** 결과로 금액 Exact·필수 필드 정확도를 비교. 지연 p95·비용 함께 기록 |

**제외 문장:** `g-dev-060`("일억일 원" 상한+1원 정정)은 텍스트 Golden에만 두고 녹음 셋에 넣지 않는다 (PM 2026-09-29 — 실제 발화로 부자연스럽고 STT 표기가 갈려 비교 잡음이 됨).

**주의.** 녹음 셋은 Dev Golden 문장에서 파생되므로 Dev와 같은 격리 규칙을 따른다. STT 튜닝(키워드 부스팅 등)에 쓴 문장도 최종 평가용에 다시 쓰지 않는다.
